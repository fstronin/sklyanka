# TDD в «Склянке»

## Цикл

1. **red** — напиши один падающий тест на одно поведение. Убедись, что он падает по ожидаемой причине,
   а не из-за компиляции или опечатки в фикстуре.
2. **green** — минимальный код, который делает его зелёным. Захардкоженная константа допустима,
   если следующий тест её выбьет.
3. **refactor** — чистишь код и тесты при зелёном прогоне, поведение не меняешь.

Шаг цикла — не больше одного поведения. Два новых `assert` про разные вещи — два цикла.
Не переходи к следующему тесту, пока предыдущий не зелёный и рефакторинг не сделан.

**Дефект сначала воспроизводится падающим тестом, потом чинится.** Тест на дефект остаётся в наборе
навсегда и в `TDD.md` помечается номером задачи или описанием инцидента.

## Формат docs/tasks/SKL-NN/TDD.md

Разделы ровно в этом порядке:

```
## Что тестируем и чем
## Уровни тестов
## Список тестов по порядку
## Тестовые данные и фикстуры
## Что специально не тестируем и почему
## Риски проверки
```

- **Что тестируем и чем** — какое поведение задачи покрываем, какими инструментами, где лежат тесты.
- **Уровни тестов** — какие уровни задействованы в этой задаче и почему именно они.
- **Список тестов по порядку** — нумерованные шаги цикла, см. ниже.
- **Тестовые данные и фикстуры** — фиксированные даты, профиль, лекарства, начальные остатки;
  имена билдеров фикстур.
- **Что специально не тестируем и почему** — чужой код, UI-мелочи, сценарии `@manual`, отложенное во вторую версию.
- **Риски проверки** — где тест может быть зелёным при сломанном продукте (часы, реальные будильники,
  фоновые ограничения EMUI) и чем это компенсируем.

### Формат пункта «Список тестов по порядку»

Каждый пункт — четыре строки:

```
1. `pendingIntakeBecomesMissedAfterWindowCloses`
   - red: приём в 08:00 остаётся «ожидается» после наступления 26 сентября 00:00 — ожидание «пропущен».
   - green: в расчёте состояния сравнить scheduled_at с границей окна и вернуть missed.
   - refactor: вынести границу окна в правило домена, убрать дублирование с проверкой конца курса.
```

Имя теста — английский `backtick`-идентификатор в стиле JUnit, читается как утверждение о поведении.
Порядок пунктов — это порядок написания тестов: от простого правила к граничным случаям.

## Уровни тестов и когда какой

| Уровень | Чем | Когда |
|---|---|---|
| Домен на JVM | JUnit5 + Kotest assertions | По умолчанию и большинство тестов: правила приёма, окна, остаток, генерация расписания |
| Room | in-memory база, `Room.inMemoryDatabaseBuilder` | Схема, запросы, миграции, каскады и уникальные индексы |
| ViewModel | kotlinx-coroutines-test (тестовый диспетчер) + Turbine для Flow | Состояния экрана, последовательность эмиссий, реакция на действия |
| Compose UI | `createComposeRule` | Состояния экрана из макетов: пусто, плотный день, чужой профиль |
| Инструментальные | на устройстве/эмуляторе | Уведомления, каналы, разрешения, будильники, Wear Engine |
| Ручные | чек-лист на эталонном устройстве | Энергосбережение EMUI, перезагрузка, смена часового пояса, часы. Сценарии `@manual` |

Правило выбора: поведение, выразимое чистой функцией домена, тестируется на JVM. Подниматься уровнем
выше можно, только если ниже это поведение не проверяется в принципе.

## Правила проекта

- **Время в домене инжектируется через абстракцию часов** и никогда не берётся из
  `System.currentTimeMillis()`, `LocalDate.now()` или `Instant.now()` напрямую. Иначе сценарии с окнами
  приёма, полуночью, концом курса и сменой часового пояса непроверяемы. В тестах — управляемая
  реализация часов, время двигается явно.
- **AlarmManager, планировщик напоминаний и Wear Engine прячутся за интерфейсами** и в тестах
  подменяются. Тест домена не знает о существовании Android-фреймворка.
- **Никакого `Thread.sleep` и ожиданий по таймауту** в тестах. Корутины — через тестовый диспетчер,
  Flow — через Turbine, время — через часы.
- Тест не зависит от порядка выполнения и от результатов другого теста.
- Имена тестов на английском, описания и комментарии — по необходимости, тексты приёмки на русском
  живут в `acceptance.feature`.

## Пример одного полного цикла

Правило: «Отметка идемпотентна по `intake_id`; выигрывает первая по `acted_at`».

**red.** Пишем падающий тест:

```kotlin
@Test
fun `markingAlreadyMarkedIntakeKeepsFirstResult`() {
    val clock = MutableClock(at("2026-09-25T08:05"))
    val intake = pendingIntake(scheduledAt = at("2026-09-25T08:00"))
    val service = IntakeMarking(repo, clock)

    service.mark(intake.id, TAKEN, source = PHONE)
    clock.advanceTo(at("2026-09-25T08:06"))
    service.mark(intake.id, SKIPPED, source = WATCH)

    repo.find(intake.id).status shouldBe TAKEN
    repo.find(intake.id).actedAt shouldBe at("2026-09-25T08:05")
}
```

Прогон: тест падает — вторая отметка перезаписала состояние на `SKIPPED`.

**green.** Минимальный код: в `mark` сначала читаем запись и выходим без изменений, если её статус
уже не `PENDING`. Тест зелёный, остальные тесты набора остались зелёными.

**refactor.** Ранний выход превращаем в явную проверку правила домена (`Intake.canBeMarked()`),
вызываем её из одного места, снимаем дублирование с обработчиком отметки с часов. Прогон зелёный,
поведение не менялось.

**Следующий шаг цикла** — отдельный тест на то, что вторая отметка не списывает остаток повторно.

## Самопроверка

- [ ] Каждый сценарий `acceptance.feature`, кроме `@manual`, имеет тест в списке.
- [ ] Каждый тест проверяет одно поведение и падал до написания кода.
- [ ] Время нигде не берётся из системных часов напрямую.
- [ ] Фреймворковые зависимости подменены, `Thread.sleep` отсутствует.
- [ ] Раздел «Что специально не тестируем и почему» заполнен, а не пуст.
