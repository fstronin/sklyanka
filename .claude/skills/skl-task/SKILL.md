# Как завести задачу SKL-NN

## 1. Выбрать номер

Возьми таблицу раздела 4 в `PLAN.md` и список в `docs/tasks/README.md`, сверься с `ls docs/tasks/`.
Номер — следующий свободный, двузначный, без переиспользования номеров закрытых задач.
Номер не меняется никогда: он уходит в ветки, коммиты и ссылки.

## 2. Собрать вход

Прочитай до того, как писать:

- `design/SPEC-original.md` — раздел, к которому относится задача;
- `docs/spec/` — рабочую спецификацию области (она главнее исходника при расхождении);
- `design/screens/*.dc.html` — макеты экранов, если задача про интерфейс;
- `docs/spec/11-glossary.md` — чтобы термины совпали с остальными документами;
- `docs/spec/12-open-questions.md` — вдруг задача упирается в нерешённый вопрос.

## 3. Создать четыре файла

```
docs/tasks/SKL-NN/
  task.md            — что и зачем, аналитическое описание
  acceptance.feature — сценарии приёмки на русском Gherkin (скилл acceptance-feature)
  TDD.md             — план тестов и порядок их написания (скилл tdd)
  TODO.md            — рабочий чек-лист исполнителя (скилл todo)
```

Ни один из четырёх не опционален. Пустая заглушка хуже отсутствия — пиши по существу.

## 4. Обновить план

- `PLAN.md`: строка в таблице раздела 4 — ID, название, этап, зависимости, статус `не начата`.
  Если задача меняет состав этапа — поправь и текст этапа в разделе 3.
- `docs/tasks/README.md`: строка со ссылкой на каталог задачи и одной фразой о результате.
- Новый открытый вопрос, всплывший при написании задачи, — в `docs/spec/12-open-questions.md`,
  а не в тексте задачи как риторический вопрос.

## 5. Стиль описания

Пиши как бизнес- или системный аналитик, а не как автор тикета «сделай вот так»:

1. Сначала бизнес-контекст: чья боль, что человек не может сделать сегодня, чем это грозит продукту.
2. Потом механика «как есть» — аналитически: какие сущности, состояния и переходы участвуют, где обрывается цепочка.
3. Потом рекомендации, а не предписанная реализация.
4. Критерии приёмки — про наблюдаемый результат и поведение, не про способ.

Жёсткие ограничения:

- Никаких номеров строк и дампов кода. Технические идентификаторы (`Intake`, `status`, `scheduled_at`,
  имя экрана из макета) — да, там, где они экономят абзац объяснений.
- Не назначай классы, паттерны и библиотеки: это работа разработки.
- Рекомендательный раздел закрывай ровно фразой: «конкретная реализация — на усмотрение разработки».
- Название задачи — результат, а не способ. «Отметка приёма и жизненный цикл Intake», а не «Добавить метод markTaken».

## 6. Шаблон task.md

```
# SKL-NN · <Название задачи, названное результатом, а не способом>

| | |
|---|---|
| Этап | N — <название> |
| Зависит от | SKL-XX, SKL-YY |
| Блокирует | SKL-ZZ |
| Статус | не начата |
| Источники | design/SPEC-original.md §N · docs/spec/XX-*.md · design/screens/*.dc.html |

## Контекст
## Задача
## Требования
## Рекомендации по решению
## Критерии приёмки
## Вне рамок
## Открытые вопросы
## Связанные материалы
```

## 7. Что писать в каждом разделе

**Шапка-таблица.** Этап — из `PLAN.md`. «Зависит от» — задачи, без результата которых эта не
начинается; «Блокирует» — те, кто ждёт эту. Прочерк, если пусто. «Источники» — конкретные разделы
и файлы, не «спека».

**Контекст.** 3–6 предложений: зачем это пользователю и продукту, что происходит сегодня без этой
задачи. Здесь же — почему задача идёт именно на этом этапе, если это неочевидно.

**Задача.** Один абзац: какой наблюдаемый результат появляется у приложения, когда задача закрыта.
Формулируй через изменение поведения системы, а не через список файлов.

**Требования.** Маркированный список. Каждый пункт ссылается на код требования из рабочей
спецификации: ПР-1 (приём и отметка), НАП-1 (напоминания), ЧАС-1 (часы), ПРФ-1 (профили),
ПЕР-1 (перенос данных), НФТ-1 (нефункциональные). Формат: `ПР-3 — отметка идемпотентна по intake_id`.
Требование, которого нет в спецификации, сначала заводится в `docs/spec/`, потом цитируется здесь.

**Рекомендации по решению.** Механика «как есть» и варианты «как может быть». Разбирай развилки
честно: что даёт вариант, чем платим. Допустимо назвать предпочтительный вариант и объяснить почему.
Последняя строка раздела — «конкретная реализация — на усмотрение разработки».

**Критерии приёмки.** Нумерованный список, каждый пункт проверяем без доступа к исходникам:
наблюдаемое поведение, состояние данных, видимый результат на экране. Формулировка — утверждение
о системе, не задание исполнителю. Плохо: «покрыть тестами генерацию приёмов». Хорошо: «для курса
с тремя приёмами в день на семь дней создаётся 21 запись приёма, по три на каждую дату курса».
Каждому критерию обязан соответствовать хотя бы один сценарий в `acceptance.feature` — при
расхождении правь оба файла сразу.

**Вне рамок.** Что сознательно не делаем в этой задаче и куда это уехало (номер задачи, вторая
версия, открытый вопрос). Это защита от расползания объёма.

**Открытые вопросы.** Только те, что мешают начать или могут изменить приёмку. Каждый — со ссылкой
на строку в `docs/spec/12-open-questions.md` и указанием, кто отвечает.

**Связанные материалы.** Макеты, ADR, соседние задачи, внешняя документация (Wear Engine,
AlarmManager) — списком со ссылками.

## 8. Самопроверка перед коммитом

- [ ] Название задачи называет результат.
- [ ] Каждое требование имеет код из спецификации.
- [ ] Каждый критерий приёмки проверяем и имеет сценарий в `acceptance.feature`.
- [ ] В тексте нет предписанной реализации, есть фраза про усмотрение разработки.
- [ ] Нет номеров строк и кусков кода.
- [ ] Созданы все четыре файла задачи.
- [ ] `PLAN.md` и `docs/tasks/README.md` обновлены, зависимости в обе стороны согласованы.
