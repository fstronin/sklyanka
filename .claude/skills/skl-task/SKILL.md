```

```

|---|---|---|
| `docs/tasks/SKL-NN/task.md` | Постановка: контекст, задача, требования, критерии приёмки | этот скилл |
| `docs/tasks/SKL-NN/acceptance.feature` | Бизнес-приёмка на русском Gherkin | `skl-task-acceptance` |

Порядок жёсткий: дизайн опирается на acceptance, план имплементации — на дизайн. Не перепрыгивай: `TDD.md` без согласованного `acceptance.feature` — гадание.

**Существующие файлы не перезаписывай без явного подтверждения** — ни один из четырёх.

## 1. Выбрать номер

Сверься с таблицей раздела 4 в `PLAN.md`, реестром `docs/tasks/README.md` и `ls docs/tasks/`. Номер — следующий свободный, двузначный, номера закрытых задач не переиспользуются. Номер не меняется никогда: он уходит в ветки, коммиты, теги Gherkin (`@SKL-NN`) и ссылки.

## 2. Собрать вход

Прочитай до того, как писать:

- `design/SPEC-original.md` — относящийся раздел (неприкосновенный исходник);
- `docs/spec/` — рабочую спецификацию области; при расхождении с исходником главнее она;
- `docs/adr/` — принятые архитектурные решения;
- `design/screens/*.dc.html` — макеты, если задача про интерфейс;
- `CONTEXT.md` — чтобы термины совпали с остальными документами;
- `docs/spec/12-open-questions.md` — вдруг задача упирается в нерешённый вопрос.

Требования неполны или противоречивы — задай вопросы пользователю **до** написания, не выдумывай.

## 3. Стиль описания задачи

Пиши как бизнес- или системный аналитик, а не как автор тикета «сделай вот так»:

1. Сначала бизнес-контекст: чья боль, что человек не может сделать сегодня, чем это грозит продукту.
2. Потом механика «как есть» — аналитически: какие сущности, состояния и переходы участвуют, где обрывается цепочка.
3. Потом рекомендации, а не предписанная реализация.
4. Критерии приёмки — про наблюдаемый результат и поведение, не про способ.

Ограничения:

- Никаких номеров строк и дампов кода в `task.md`; file:line живёт в `TDD.md`.
- Технические идентификаторы (`Intake`, `status`, `scheduled_at`, имя экрана из макета) — там, где экономят абзац объяснений.
- Не назначай классы, паттерны и библиотеки: это работа дизайна.
- Рекомендательный раздел закрывай фразой: «конкретная реализация — на усмотрение разработки».
- Название задачи — результат, а не способ: «Отметка приёма и жизненный цикл Intake», а не «Добавить метод markTaken».

## 4. Шаблон task.md

```
# SKL-NN · <Название задачи, названное результатом, а не способом>

| | |
|---|---|
| Этап | N — <название> |
| Зависит от | SKL-XX, SKL-YY |
| Блокирует | SKL-ZZ |
| Статус | не начата |
| Источники | design/SPEC-original.md §N · docs/spec/XX-*.md · design/screens/*.dc.html |

## Контекст
## Задача
## Требования
## Рекомендации по решению
## Критерии приёмки
## Вне рамок
## Открытые вопросы
## Связанные материалы
```

**Шапка.** Этап — из `PLAN.md`. «Зависит от» — задачи, без результата которых эта не начинается; «Блокирует» — те, кто ждёт эту; прочерк, если пусто. «Источники» — конкретные разделы и файлы, не «спека».

**Контекст.** 3–6 предложений: зачем это человеку и продукту, что происходит сегодня без задачи, почему она стоит на этом этапе.

**Задача.** Один абзац: какой наблюдаемый результат появляется у приложения, когда задача закрыта. Через изменение поведения системы, а не через список файлов.

**Требования.** Маркированный список; каждый пункт ссылается на код требования из рабочей спецификации: ПР-1 (приём и отметка), НАП-1 (напоминания), ЧАС-1 (часы), ПРФ-1 (профили), ПЕР-1 (перенос данных), НФТ-1 (нефункциональные). Формат: `ПР-3 — отметка идемпотентна по intake_id`. Требования, которого нет в спецификации, сначала заводится в `docs/spec/`, потом цитируется здесь.

**Рекомендации по решению.** Механика «как есть» и варианты «как может быть», честно: что даёт вариант, чем платим. Допустимо назвать предпочтительный и объяснить почему. Последняя строка раздела — «конкретная реализация — на усмотрение разработки».

**Критерии приёмки.** Нумерованный список, каждый проверяем без доступа к исходникам. Плохо: «покрыть тестами генерацию приёмов». Хорошо: «для курса с тремя приёмами в день на семь дней создаётся 21 запись приёма, по три на каждую дату курса». Каждому критерию соответствует хотя бы один сценарий в `acceptance.feature`; при расхождении правь оба файла.

**Вне рамок.** Что сознательно не делаем и куда это уехало (номер задачи, вторая версия, открытый вопрос).

**Открытые вопросы.** Только мешающие начать или способные изменить приёмку; каждый — со ссылкой на `docs/spec/12-open-questions.md` и ответственным.

**Связанные материалы.** Макеты, ADR, соседние задачи, внешняя документация (Wear Engine, AlarmManager).

## 5. Обновить реестры

- `PLAN.md`: строка в таблице раздела 4 — ID, название, этап, зависимости, статус `не начата`. Если меняется состав этапа — поправь текст этапа в разделе 3.
- `docs/tasks/README.md`: строка со ссылкой на каталог задачи и одной фразой о результате.
- Новый открытый вопрос, всплывший при написании, — в `docs/spec/12-open-questions.md`, а не риторическим вопросом в тексте задачи.
- Статусы (`не начата` · `в работе` · `на проверке` · `выполнена` · `заблокирована`) обновляются в обоих реестрах одновременно.

## 6. Ведение задачи в работе

1. Читать `task.md` и `acceptance.feature`.
2. Идти по `TODO.md`, отмечая выполненное `✅`; новые потребности — новыми пунктами, старые не править.
3. Расхождение дизайна с кодом или acceptance — обсудить с пользователем и синхронизировать документ, а не молча отклониться.
4. Работа сверх объёма задачи не делается молча: заводится отдельная `SKL-NN`.
5. Задача закрыта, когда сценарии `acceptance.feature` зелёные, `@manual` проверены на эталонном устройстве, `TODO.md` пройден, статусы обновлены.

## 7. Самопроверка перед коммитом

- [ ] Название задачи называет результат.
- [ ] Каждое требование имеет код из спецификации.
- [ ] Каждый критерий приёмки проверяем и имеет сценарий в `acceptance.feature`.
- [ ] В `task.md` нет предписанной реализации, есть фраза про усмотрение разработки.
- [ ] Созданы артефакты в нужном порядке, существующие файлы не затёрты.
- [ ] `PLAN.md` и `docs/tasks/README.md` обновлены, зависимости согласованы в обе стороны.
