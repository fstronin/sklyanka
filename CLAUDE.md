# Склянка — соглашения проекта

Мобильное приложение для учёта приёма лекарств. Android, HMS, русский язык интерфейса.
Исходная спецификация заказчика — `design/SPEC-original.md`, макеты — `design/screens/`.

## Где что лежит

| Путь | Содержание |
|---|---|
| `PLAN.md` | План разработки, этапы, статусы задач |
| `docs/spec/` | Рабочая спецификация: суть, цели, требования по областям |
| `docs/spec/adr/` | Архитектурные решения (ADR) |
| `docs/spec/13-monetization.md` | План монетизации и продуктовая стратегия (ведёт агент product-manager) |
| `docs/spec/product-decisions.md` | Журнал продуктовых решений и их влияния |
| `docs/tasks/SKL-NN/` | Артефакты задачи: `task.md`, `acceptance.feature`, `TDD.md`, `TODO.md` |
| `design/` | Неприкосновенный исходник: спека заказчика и HTML-макеты |
| `.claude/skills/` | Скиллы проекта: как писать задачу, Gherkin, TDD, TODO |
| `app/`, `core/`, … | Код (появится по SKL-02) |

`design/` не редактируется. Всё уточнённое и изменённое живёт в `docs/spec/`.
Исключение — агент-дизайнер (`.opencode/agent/designer.md`): он работает с макетами
`design/screens/` и может их редактировать только с явного разрешения (пользователь попросил,
либо ведущая сессия предложила и пользователь одобрил).

**Продуктовые решения проходят через агента продакт-менеджера** (`.opencode/agent/product-manager.md`):
он — единственная точка ответов «что входит в базу/премиум», «меняем ли монетизацию», «стоит ли
делать фичу», и ведёт `docs/spec/13-monetization.md` (план) и `docs/spec/product-decisions.md`
(журнал решений и их влияния). Перед принятием продуктового решения — спроси его.

## Стек

Kotlin, Jetpack Compose, Room, Hilt, AlarmManager, Wear Engine SDK. Минимум API 26.
Обоснование и альтернативы — `docs/spec/adr/ADR-0001-stack.md`.

## Язык

- Документация, задачи, Gherkin-сценарии, тексты интерфейса — **русский**.
- Код, идентификаторы, имена тестов, сообщения коммитов — **английский**.
- Доменные термины пишутся одинаково везде, см. `docs/spec/11-glossary.md`.

## Порядок работы над задачей

1. Прочитать `docs/tasks/SKL-NN/task.md` и `acceptance.feature`.
2. Идти по `TDD.md`: сначала падающий тест, потом код, потом рефакторинг.
3. Отмечать пункты в `TODO.md` по мере выполнения.
4. Задача закрыта, когда все сценарии `acceptance.feature` зелёные и `TODO.md` пуст.
5. Обновить статус задачи в `PLAN.md` и `docs/tasks/README.md`.

## Правила, которые не обсуждаются

- **Надёжность напоминания важнее всего остального.** Пропущенное напоминание — отказ продукта, а не дефект удобства.
- **Профили не смешиваются.** Интерфейс всегда в контексте ровно одного профиля.
- **Ядро работает без сети.** Прочая сеть (биллинг, синхронизация, cloud AI, push) допустима только в платном контуре («Склянка Про», «Склянка Забота»). Исключение — аналитический контур: Huawei Analytics Kit и A/B-эксперименты (A/B Testing) во всех сборках с первой публикации, по единому согласию при первом запуске, без медицинских данных, с отключением в настройках (ПМ-19/ПМ-20, `ADR-0011`). Данные о здоровье уходят наружу только по согласию и в E2E; реклама и продажа данных запрещены.
- **Приложение не медицинское изделие.** Никаких рекомендаций по лечению и подбору доз. Проверка совместимости — справочная, на LLM, с дисклеймером «может ошибаться».
- Токены визуального языка не хардкодятся по месту — только через дизайн-систему (`docs/spec/08-design-system.md`).
