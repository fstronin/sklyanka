# Склянка — поведение

Нормативный документ о поведении продукта: данные, расписание и приём, напоминания, разрешения,
экраны, профили, перенос данных. Заменяет прежний слой `docs/spec` (удалён 08.10.2026):
`01-platform.md` (ПЛ-6…ПЛ-22), `02-data-model.md`, `03-screens.md`, `04-reminders.md`,
`06-profiles.md`, `07-data-transfer.md`, `14-reminder-check-ux.md`.

Коды требований устойчивы и не перенумеровываются: ИНВ-, МГ-, ПР-, НАП-, ПЛ-, ЭКР-, ПРФ-, ПЕР-,
AC-. Соответствие старых мест новым — `05-code-map.md`; история и обоснования — `02-decisions.md`;
методы проверки — `11-quality.md`; токены и компоненты — `12-design.md`.

Пометки сверки с кодом: `[не реализовано]` — правило действует, в коде его нет; `[расхождение]` —
код ведёт себя иначе, фактическое состояние названо рядом; `[вне продукта]` — не входит, пока не
реализовано; `[снято Р-N]` — выведено из продукта решением журнала.

Пути от корня репозитория: `domain/` = `core-domain/src/main/kotlin/ru/stohastika/sklyanka/domain/`,
`data/` = `core-data/src/main/kotlin/ru/stohastika/sklyanka/data/`,
`app/` = `app/src/main/kotlin/ru/stohastika/sklyanka/`.

## 1. Данные

Три продуктовые сущности: **Profile** (кому), **Medication** (что и когда), **Intake** (что
произошло с приёмом). Приверженность, остаток и «курс» — производные и не хранятся. Связь
Profile 1—N Medication 1—N Intake; профиль приёма определяется через лекарство, собственного
поля профиля у приёма нет, а `actor_profile_id` — тот, кто поставил отметку. Хранилище — Room,
база `sklyanka.db`, версия схемы 7, шесть таблиц (`data/room/SklyankaDatabase.kt:42-101`);
три служебные — `op_log`, `reminder_log`, `deferred_reminder`.

### 1.2 Перечисления и хранение

Значения перечислений хранятся строковыми именами констант, а не порядковыми номерами: номер
ломается при вставке значения и нечитаем в файле переноса (`data/room/SklyankaConverters.kt:77-81`).

| Перечисление | Значения |
|---|---|
| `MedicationForm` | TABLET, CAPSULE, SPRAY, SYRUP, DROPS, INJECTION |
| `TabletShape` | ROUND, ROUND_SCORED, OVAL, OBLONG, TRIANGULAR |
| `FoodRelation` | ANY, BEFORE_MEAL, WITH_MEAL, AFTER_MEAL |
| `ScheduleMode` | SCHEDULED, PRN |
| `IntakeStatus` | PENDING, TAKEN, SKIPPED, MISSED |
| `IntakeSource` | PHONE, AUTO · `[снято Р-3]` WATCH |
| `ArchiveReason` | COURSE_FINISHED, MANUAL |

Вид таблетки применим только к форме TABLET: силуэт капсулы задан самой формой. Записи,
сохранённые до сужения, могли иметь непустой `shape` при другой форме; чистящая миграция не
делается — значение игнорируется отображением и исчезает при первом сохранении лекарства формой.

| Вид значения | Хранение |
|---|---|
| Перечисление | строка — имя константы |
| `times` | строка отсортированных «ЧЧ:мм» через запятую; пустая строка — пустой список |
| Дата | текст «ГГГГ-ММ-ДД» |
| Локальные дата и время | текст «ГГГГ-ММ-ДДTЧЧ:мм» |
| Момент | целое число миллисекунд: `acted_at`, `archived_at`, `deleted_at`, `occurred_at`, `fired_at`, `fire_at`, `op_log.at` |
| Десятичное | текст без экспоненты; в SQL не сравнивается |

Внешние ключи объявлены с RESTRICT на всех ссылках и включены явно:
`data/room/ForeignKeyEnforcement.kt` поднимает прагму `foreign_keys` на соединении
записи сразу после сборки базы, ею пользуются боевой граф и все тестовые сборки.
Раньше ИНВ-12 держался молчаливым умолчанием Room; продукт от него отвязан. Колбэк
`RoomDatabase.Callback` для прагмы непригоден: `onCreate`/`onOpen` исполняются внутри
транзакции создания, где `PRAGMA foreign_keys` — no-op. Включение и отказ закреплены
`ForeignKeyEnforcementTest` (инструментально, на настоящей базе).

### 1.3 Хранение времени

Раскладка нормативна и реализована; разбор — `docs/adr/0013-time-storage.md`.

| Поле | Хранение | Почему |
|---|---|---|
| `Medication.times` | локальное время без пояса | Правило, а не момент: при перелёте продолжает означать «8 утра» |
| `start_date`, `end_date` | локальная дата без пояса | Границы курса календарные, а не моментные |
| `Intake.scheduled_at` | локальные дата и время | Группировка по суткам должна быть устойчивой: в UTC приём 23:30 попал бы в чужой день |
| `Intake.acted_at` | момент в UTC | Факт: сравнение по ПР-3 обязано быть корректным при разных поясах |

Момент срабатывания будильника вычисляется из локального времени в текущем поясе и
пересчитывается при смене пояса (НАП-11). По умолчанию приёмы остаются в «своём» поясе: перелёт
не переписывает созданные записи, а человеку предлагается пересчитать приёмы текущих суток;
автоматически этого не происходит (П-4).

| Код | Инвариант | Кто держит |

| ИНВ-4 | `dose_amount > 0` | `Invariants.violations(medication)` |

### 1.5 Правила предметной области ПР-1…ПР-14

| Код | Правило |
|---|---|
| ПР-1 | «Ожидается» автоматически становится «пропущено без отметки» по истечении окна приёма; окно — до конца суток (НАП-35). При переводе `source = AUTO`, `acted_at` — момент перевода |
| ПР-2 | Отметка идемпотентна по идентификатору приёма: повторная не создаёт вторую запись и не меняет записанную |
| ПР-3 | Конфликт двух отметок одного приёма разрешается по первому `acted_at`: выигрывает более ранняя, второй пренебрегаем; сравнение по моменту отметки, а не по времени доставки. `[снято Р-3]` Второй источник (часы) выведен; правило остаётся для нажатия, доставленного позже |
| ПР-4 | У приёма «по потребности» запись создаётся в момент нажатия «Принять», `scheduled_at` равен `acted_at`; записей «ожидается» у такого режима нет |
| ПР-5 | Отметка «принято» уменьшает `stock_left` на `dose_amount`; «пропущено» и «пропущено без отметки» остаток не трогают. При пустом `stock_left` не применяется |
| ПР-6 | Пустая `end_date` — бессрочный приём: приёмы порождаются без конечной даты |
| ПР-7 | `max_per_day` заполняется только при «по потребности» |
| ПР-8 | `times` заполняется только при «по расписанию» |
| ПР-9 | `shape` заполняется только при форме «таблетка» |
| ПР-10 | Любая выборка «Сегодня», истории, остатков и статистики ограничена активным профилем; запроса, возвращающего приёмы нескольких профилей, в продуктовых экранах нет. Исключения служебные и намеренные: перевод просроченных приёмов и выбор кандидатов на напоминание охватывают все профили (`data/room/dao/IntakeDao.kt:225`, `ReminderDao.kt:43`); список исключений закреплён тестом-стражем `core-data/src/test/.../GuardTest.kt:174` |

| ПР-14 | Удаление лекарства мягкое: не порождает приёмов, не планируется, не показывается нигде — включая «Архив», историю, отчёт врачу и предупреждения об остатке; записи приёмов сохраняются в базе и переносятся файлом, но исключаются из расчёта приверженности. Удалить можно только лекарство без отметок «принято» (ИНВ-22), иначе путь один — архив. Удаление снимает будущие «ожидается» и немедленно отменяет будильники (НАП-11). Возврат — очистка `deleted_at` в окне отмены |

### 1.6 Архив, мягкое удаление, миграции МГ-1…МГ-7

Лекарство не удаляется физически никогда; два мягких состояния не взаимозаменяемы: **архив** —
след курса, виден в «Архиве», участвует в истории, отчёте и приверженности, может быть возвращён;
**удаление** — ошибочно заведённая запись, скрыта везде, приёмы остаются в базе и в файле, но не
участвуют в расчётах. Физическое удаление возможно только режимом «заменить всё» (§7).

При наступлении `end_date` приложение **предлагает** убрать курс в архив с причиной «курс
завершён», человек подтверждает (`domain/medication/CourseCompletion.kt:36`, вызов
`feature-meds/.../card/MedicationCardViewModel.kt:150`); молчаливой архивации нет. Причина
«убрано вручную» ставится при архивации из карточки. Возврат из архива с прошедшей `end_date`

## 2. Расписание и приём

### 2.1 Генерация приёмов

Приёмы порождаются окном, а не на весь курс: глубина — **7 суток включая текущие**
(`app/di/SchedulingModule.kt:44`), минимальная глубина 3 суток (`domain/schedule/GenerationWindow.kt`).
Горизонт генерации не совпадает с горизонтом планирования будильников (НАП-7) и заметно длиннее.
Порождаются только приёмы лекарства с расписанием, не архивного, не удалённого, с непустым
списком времён (`domain/schedule/ScheduleExpander.kt`); в день начала курса прошедшие времена не
порождаются, в остальные дни порождаются и переводятся в «пропущено» общим правилом.

Разница планов (`domain/schedule/IntakePlanDiff.kt`): существующая запись **любого** статуса
занимает своё время; создаются только отсутствующие моменты; снимаются только «ожидается»,
которых нет в новом плане и которые ещё в будущем. Прошедшие «ожидается» сохраняются для
перевода в «пропущено»; отмеченные не переписываются никогда. Вставка — с игнорированием
конфликта, уникальность держит индекс (ИНВ-13).

| Что случилось | Будущие «ожидается» | Причина в коде |
|---|---|---|
| Правка расписания (времена, даты, режим, доза) | пересоздаются по новому плану | `MEDICATION_SAVED`, `MEDICATION_ADDED` |
| Архивация | снимаются | `MEDICATION_ARCHIVED` |
| Возврат из архива | создаются заново | `MEDICATION_RESTORED` |
| Мягкое удаление | снимаются, будильники отменяются | `MEDICATION_DELETED` |
| Отмена удаления | создаются заново | `MEDICATION_UNDELETED` |

Причины пересборки плана (`domain/schedule/PlanReason.kt`, 13): `APP_START`, `BOOT`,
`TIMEZONE_CHANGED`, `TIME_CHANGED`, `MEDICATION_SAVED`, `MEDICATION_ARCHIVED`,
`MEDICATION_DELETED`, `MEDICATION_UNDELETED`, `MEDICATION_ADDED`, `MEDICATION_RESTORED`,
`ANCHOR_ALARM`, `MANUAL_CHECK`, `DATA_IMPORTED`. У `MANUAL_CHECK` продуктивного вызывающего
нет — кнопки «Проверить сейчас» в интерфейсе нет.

### 2.2 Статусы, окно приёма, автоперевод

| Статус | Смысл |
|---|---|
| «ожидается» | время не настало либо окно не истекло, отметки нет |
| «принято» | человек подтвердил приём |
| «пропущено осознанно» | человек явно отказался от приёма |
| «пропущено без отметки» | окно истекло, отметки не было; проставляется автоматически (ПР-1) |

Различие двух видов пропуска содержательно: решение человека против отсутствия решения; в отчёте
врачу они не смешиваются.

| Переход | Условие | Последствия |
|---|---|---|
| — → «ожидается» | планировщик создал приём по расписанию | — |
| — → «принято» | нажата «Принять» у лекарства «по потребности» | запись создаётся отмеченной, `scheduled_at = acted_at` (ПР-4), остаток списывается (ПР-5) |
| «ожидается» → «принято» | отметка «Принято» | `acted_at`, `source = PHONE`, `actor_profile_id` по ПР-12, остаток уменьшается на дозу |
| «ожидается» → «пропущено осознанно» | отметка «Пропустить» | те же поля; остаток не трогается |
| «ожидается» → «пропущено без отметки» | истекло окно (ПР-1) | `acted_at` — момент перевода, `source = AUTO`, `actor_profile_id` пусто; остаток не трогается; уведомление не порождается |

| «принято» → снято (запись «по потребности») | «Отменить» в коротком окне (Р-46) | `revoked_at` заполняется, статус остаётся «принято», списанная доза возвращается; запись исчезает из истории, остатка, счёта приёмов и лимита |

Из трёх отмеченных статусов исходящих переходов нет: новое решение не переписывает поставленный
статус (ПР-2). Единственное исключение — замещение более ранним `acted_at` (ПР-3): это то же
нажатие, дошедшее позже, а не новое решение; доза второй раз не списывается.

**НАП-35.** Окно, после которого «ожидается» становится «пропущено без отметки», — **до конца
суток**: неотмеченный приём переходит в 00:00 следующих суток. Граница — параметр домена, а не
константа перехода (`domain/intake/IntakeWindow.kt:46-60`, реализация `EndOfDayIntakeWindow`);
от неё зависят расчёт приверженности и момент снятия уведомления. Отметка,
сделанная до конца суток, попадает в «принято»; признак «вовремя» определяется отдельным окном
[−2 ч, +2 ч] и с границей суток не связан — метрика «принято вовремя» считается по плановым
приёмам (Р-21, Р-27; §5.5).

**НАП-34.** Автоперевод выполняется не только по таймеру, но и при каждом открытии приложения и
при каждом перепланировании: устройство могло быть выключено в момент истечения окна. Причины
(`domain/intake/SweepMissedIntakesUseCase.kt`): `TIMER`, `APP_START`, `REPLAN`. Перевод снимает
показанные карточки этих приёмов и пишет в журнал `MISSED_SWEEP`.

### 2.3 Отметка и её отмена

Единственная точка отметки — `domain/intake/MarkIntakeUseCase.kt`; отметка с источником `AUTO`
через неё невозможна. Идемпотентность (ПР-2, ИНВ-19) держится условным запросом: вторая отметка
меняет ноль строк и даёт исход «проигнорировано», остаток не трогается. Замещение более ранней
отметкой (ПР-3) — отдельный условный запрос `WHERE acted_at > :actedAt`.

Отмена ошибочной отметки — в коротком окне **5 секунд** (коридор 4–6): снэкбар «Отменить»
возвращает приём в «ожидается», возвращает списанную дозу, пишет след в журнал и повторно
напоминание не поднимает. Задним числом история не правится: длинного окна и изменения статуса
из карточки приёма или истории нет; поздняя ошибка заменяется новым решением. Окно держит
`domain/undo/UndoableActionStore.kt:98`, сам сценарий отмены время не проверяет.

Отмена приёма **«по потребности»** устроена иначе (Р-46): в том же 5-секундном окне запись
**снимается** мягким признаком «снято», а не переводится в «ожидается», и списанная доза
возвращается. Термины глоссария: «Снятие записи» (действие) и «Снятая запись» (состояние) — про
«по потребности»; «Отмена отметки» остаётся только за плановыми приёмами. Физического удаления
нет: список допустимого `DELETE` в `ADR-0012` п. 5 не расширяется. Факт снятия пишется в журнал
операций без медицинских данных (НФТ-19); снятая запись невидима в истории и остатке и напоминаний
не порождает. Реализовано SKL-127: `IntakeRepositoryImpl.undoAtomically` делит действие по режиму
лекарства — плановая отметка возвращается в «ожидается», а запись «по потребности» снимается
признаком `revoked_at` (миграция 8→9). Видимость держит выборка хранилища: `revoked_at IS NULL`
стоит в выборках дня, периода и по лекарству, в счёте суток (лимит «по потребности») и в проверке
ИНВ-22 — снятая запись не мешает удалить лекарство. Повторное снятие меняет ноль строк и дозу
второй раз не возвращает.

### 2.4 Остаток упаковки

Списание (`domain/stock/StockLedger.kt`): «принято» — уменьшить на дозу, возврат из «принято»
при отмене — восстановить, остальные статусы — не трогать. Ниже нуля остаток не опускается:
значение обрезается по нулю, факт обрезки сохраняется. При пустом `stock_left` правило не
применяется.

Прогноз «хватит на N дней» (`domain/stock/StockForecast.kt`): суточный расход = доза × число
времён; для «по потребности» не определён и не показывается; число дней — целая часть от деления,
потолка нет. Порог настраивается на лекарство: варианты 3 / 5 / 7 / 10 / 14 дней, по умолчанию 7
(`domain/stock/StockThresholds.kt:17-20`); при выключенном напоминании порог очищается.
Пополнение (`RefillStockUseCase`) заменяет значение остатка и не меняет размер упаковки;
отрицательное значение отклоняется.

### 3.3 Восстановление до разблокировки

**НАП-44.** Раннее восстановление опирается на **снимок будильников** — зеркало поставленных
будильников в хранилище, доступном до ввода кода. Снимок обновляется в той же точке, где
будильник ставится и снимается, поэтому отложенные и отменённые срабатывания входят в него без
отдельного пути. Состав записи — адрес и момент: идентификатор приёма, абсолютный момент, номер
показа (`domain/reminder/DirectBootAlarms.kt`); названий лекарств, дозировок, имён и
идентификаторов профилей в снимке нет. До разблокировки приложение не предъявляет уведомлений с
медицинскими данными. Хранилище — `data/prefs/DeviceProtectedDirectBootStore.kt`.

Отбраковка (`domain/reminder/DirectBootReplayPolicy.kt:34-52`): снимок отбрасывается целиком при
чужой версии формата, превышении потолка записей, возрасте старше горизонта планирования и
отметке времени в будущем сверх допуска; поштучно пропускаются записи с пустым адресом, номером
показа вне диапазона и прошедшим моментом. Частичное восстановление из подозрительного снимка
запрещено: неверные будильники хуже отсутствия, пересборка после разблокировки восстановит верные.

Деградация безопасна и явна: снимка нет, файл повреждён, снимок устарел или версия чужая —
будильники не ставятся, приложение не падает, след попытки доходит до журнала после
разблокировки (НАП-14). Приоритет за полной пересборкой: набор, собранный после разблокировки,
старший; пересборка видит восстановленные записи и снимает всё, что разошлось с планом.

Шаг «Уведомления» проверяет три состояния: разрешение, канал уведомлений, полноэкранные
уведомления. Причина называется теми же словами, что в баннере «Сегодня» и в диагностике: одно
перечисление называют три экрана (`domain/reminder/ReminderReliability.kt`). Порядок причин —
«не приходят» (уведомления, затем канал) выше «опаздывают» (точные будильники) выше
«показываются не полностью» (полноэкранные); при выключенных уведомлениях канал отдельно не
называется; устоявшаяся пара «уведомления + точные будильники» называется одной фразой.

Входы в коде: первый запуск (`app/MainActivity.kt:304`), предупреждение «Сегодня» (`:320`),
баннер перерыва (`:390`), настройки и «Пройти настройку заново» через `PermissionsActivity`.
Индикатор шагов рисуется только при первом запуске. Системная «Назад» на первом запуске работает
как пропуск: экран отмечается просмотренным, человек попадает на «Сегодня» с предупреждением,
при следующем запуске онбординг сам не открывается.

**Плотный день.** Включается при числе приёмов больше десяти. Свёртка по времени суток: прошедшая
группа сворачивается в блок с итогом, текущая разворачивается со счётчиком, будущая сворачивается
с числом приёмов впереди. Одновременные приёмы — по одной строке с подписью группы «N приёмов ·

каждый отдельной записью, остаток списывается по каждому лекарству. Подтверждение сбрасывается
нажатием вне кнопки, отметкой строки, уходом с экрана и через 10 секунд; сброс молчаливый;

которой наступило; отмена — тем же снэкбаром, возвращает все приёмы действия.

**Чужой профиль.** Индикация — §6. Снэкбар тот же; акцент действия «Отменить» — цвет профиля,
отдельного текста про профиль у снэкбара нет: контекст несут постоянные признаки.

### 5.3 Лекарства, карточка, архив, форма

**Список.** Заголовок, сегментный переключатель «Активные · N» / «Архив · N», карточки, круглая
кнопка добавления 60 dp над нижней панелью. В карточке: плитка силуэта «форма + вид», название,
строка описания (форма и доза), строка расписания одной фразой «частота · времена · период либо
остаток», шеврон.

| Код | Требование |
|---|---|
| ЭКР-3 | Счётчик «Активные» считает только лекарства с расписанием; «по потребности» показываются в списке, но в счётчик не входят (`core-domain/.../medication/MedicationListRules.kt:44`) |
| ЭКР-4 | Строка расписания показывает остаток, когда сработал порог, и период приёма в остальных случаях; одновременно остаток и период не показываются |
| ЭКР-5 | Карточка «по потребности» отличается составом строк: чип «по потребности» у названия, ограничение «не чаще N раз в сутки» в конце описания, третья строка «последний приём — дата», кнопка «Принять» вместо шеврона |
| ЭКР-10 | Порядок активных — «что ближе, то выше»: по ближайшему следующему приёму, при равном времени — по названию; «по потребности» и лекарства без ближайшего приёма стоят ниже и упорядочены по названию. **Карточка лекарства.** Шапка с возвратом и «Изменить»; титул с плиткой силуэта, названием и
подписью; блоки «Расписание», «Курс», «Остаток», «Последние 7 дней»; внизу «В архив» либо
«Вернуть», под ней при доступности — тихое «Удалить» опасным цветом с пояснением «Удалить можно,
пока нет ни одной отметки „принято“». Строки «Напоминать на часах» и выбора звука нет;
`[снято Р-3]` тумблер часов подлежит удалению вместе с швом.

| Код | Требование |
|---|---|
| ЭКР-6 | В блоке «Последние 7 дней» текущий день не засчитывается ни в принятые, ни в пропущенные, пока сутки не закончились: кружок рисуется полым с обводкой, счётчик недели считает только завершившиеся дни |
| ЭКР-7 | Подпись под названием собирается одной строкой из четырёх сведений в порядке «форма · вид таблетки · дозировка препарата · связь с едой»; вид входит в подпись только для форм, к которым применим (ПР-9) |

Состояния карточки: бессрочный курс — без полосы и «осталось N дней»; порог остатка не сработал —
предупреждение и тревожный цвет полосы снимаются; учёт остатка выключен — блок скрыт целиком;
«по потребности» — вместо расписания ограничение в сутки, блок «Курс» скрыт, в неделе
показываются фактические приёмы; в архиве — «Вернуть» вместо «В архив»; история короче недели —
дни до начала курса пустые; завершённых дней с приёмами нет — вместо счётчика фраза «Приёмов
пока нет», «0 из 0» и «0 %» не показываются, при этом «0 из 14» остаётся числом. Действие
«Удалить» показывается только при отсутствии отметок «принято»; после первой такой отметки
действия нет вовсе — ни серой кнопки, ни пояснения.

**Удаление лекарства.** Шторка подтверждения с названием и пояснением, что сразу после удаления
лекарство можно вернуть; действия — «Удалить» опасным цветом и тихое «Отмена»; «Отмена»,
системная «Назад» и тап вне шторки закрывают её без изменений. После удаления карточка
закрывается, человек возвращается туда, откуда её открыл, и на этом экране 5 секунд живёт
снэкбар с действием «Отменить»: лекарство исчезает из списков, «Архива» и «Сегодня», счётчики
уменьшаются, новых приёмов не порождает; «Отменить» возвращает лекарство, приёмы и будильники;
после окна вернуть через интерфейс нельзя, уход с экрана окно закрывает. Шторка собрана из
`SklyankaBottomSheet` и подтверждается вводом слова «Удалить» тем же компонентом, что удаление
профиля и режим «Заменить всё» (Р-14, §5.7; SKL-105).

**Архив.** Тот же заголовок и переключатель, выбрана позиция «Архив». Две группы по причине:
«Курс завершён» и «Убрано вручную»; пустая группа скрывается целиком, при пустом архиве сегмент
остаётся доступным и показывается пояснение. Поясняющая плашка «История приёмов сохраняется.
Возврат из архива восстановит лекарство с прежним расписанием.» Возврат очищает поля архива,
восстанавливает расписание, создаёт приёмы и планирует будильники; при прошедшей дате окончания
показывается плашка о необходимости обновить период. Из архивного вида карточки доступно и
«Удалить» с тем же условием.

| Код | Требование |
|---|---|
| ЭКР-8 | Подпись в карточке архива определяется причиной: при «курс завершён» — итог приверженности курса, при «убрано вручную» — дата помещения в архив; подписи не взаимозаменяемы |
| ЭКР-9 | Экран «Архив» показывает поясняющую плашку о сохранности истории: сохранность заявляется текстом, а не подразумевается |

**Форма лекарства.** Действия в шапке нет вовсе (Р-54): выход — системный «Назад», сохранение одно —
нижняя кнопка (Д-3, §5.1). Заголовок формы — крупный, тем же `TitleScreen` (Literata 30/600, слева),
что у «Настроек», «Лекарств» и «Сегодня», на боковом поле шапки 20 dp. Шапка подчиняется общему
паттерну прокрутки (§7 `12-design.md`): крупный заголовок — контент и уезжает вместе с содержимым,
а поверх по порогу остаётся закреплённый ряд 56 dp **только** с компактным заголовком — ни шеврона,
ни действия в нём нет, и возврат в форму не рисуется даже выключенным.
Порядок блоков: название → превью
выбора → форма выпуска → вид таблетки → доза на один приём → режим приёма → расписание (число
приёмов в сутки и времена **или** максимум в сутки) → связь с едой → остаток в упаковке → период
приёма → закреплённая кнопка сохранения. Переключатель режима стоит выше расписания: он
определяет, нужно ли время; кнопка сохранения одна — нижняя.

Форма выпуска — сетка 3×2 из шести плиток с силуэтами; вид таблетки — ряд из пяти кнопок, только
при форме «таблетка», необязателен, при смене формы сбрасывается. Превью обновляется вместе с
черновиком: силуэт, заголовок «Форма вид», подпись. Режим «по потребности» скрывает блоки
расписания и связи с едой и показывает ввод максимума в сутки. Единица остатка зависит от формы
выпуска, а слово единицы в поле согласуется с набранным числом (§5.3 `12-design.md`):
«1 таблетка», «2 таблетки», «5 таблеток», «0,5 таблетки», а в пустом поле — имя единицы:
таблетка, капсула, мл, капля, впрыск, инъекция. Блок остатка: «Сейчас есть», «Размер упаковки» (необязательное, с
подсказкой), «Напомнить о покупке» с тумблером и рядом чипов порога 3 / 5 / 7 / 10 / 14, по
умолчанию 7. Блок периода: «Начало», «Принимать бессрочно» с тумблером, «Окончание» и пресеты
срока — 1 неделя, 2 недели, 1, 2, 3, 6 месяцев, 1 год и «Другая дата»; пресеты приглушены, пока
курс бессрочен; выбор ставит дату окончания календарным расчётом от даты начала; отмечен пресет,
чья дата совпала с текущей, произвольная дата не отмечает ни одного. Диалоги даты и времени —
компоненты дизайн-системы, а не системные диалоги прошивки; 12/24 — из системной настройки. При
незаполненном названии сохранение недоступно; нарушений валидации 11, форма прокручивается к
первому. Правка существующего лекарства — та же форма с названием в заголовке.

### 5.4 Напоминание

Тёмная поверхность, полноэкранная карточка поверх блокировки; состав — НАП-29, действия — НАП-30.
Основная кнопка «Принято» во всю ширину, второстепенные «Отложить N мин» и «Пропустить» — равные
половины строки; иерархию несут заливка и подпись, а не размер. Ряд сохраняется, пока каждая
подпись одной строкой влезает в половину ширины ряда с боковым зазором не меньше 4 dp; иначе обе
кнопки встают столбиком во всю ширину. Порог — по фактической ширине подписи, а не по масштабу
шрифта: при 200 % столбик во всех локалях; подпись не переносится и не обрезается. В карточке из
нескольких приёмов каждая пара кнопок — равные половины карточной формы, как в карточке приёма.

Снэкбара на карточке нет: отмена показывается на «Сегодня», чтобы полноэкранное напоминание
осталось экраном одного решения. Снэкбар получает только действие, **закрывшее** карточку, —
отметка единственной строки или нижние кнопки на все оставшиеся приёмы. Частичная отметка одной
строки в карточке из нескольких приёмов карточку не закрывает и отмены не получает: отмеченная
строка исчезает, человек остаётся в том же напоминании. Если карточку закрывает последняя по
счёту отметка строки, снэкбар относится к ней. Отменённый приём напоминание повторно не
поднимает: будильник уже сработал.

Состояния: «по потребности» — экран не показывается; настойчивое напоминание — экран поднимается
повторно, отдельного вида у повторного показа нет; опоздавшее срабатывание — не показывается
вовсе (НАП-33), а если показано, карточка не отличается от обычной: время плановое, отклонение
видно в диагностике; отметка уже поставлена иным путём — экран закрывается сам (НАП-32).

### 5.5 История и отчёт врачу

Состав: шапка с возвратом и «Отчёт врачу», заголовок, три плитки сводки, календарь месяца с
переключателем и легендой, разбивка «По лекарствам» с процентами и полосами, строка вывода о
самом пропускаемом приёме. Нижней панели нет.

Плитка «принято вовремя» показывает долю отметок, попавших в окно **[−2 ч, +2 ч]** вокруг
назначенного времени приёма (Р-21, Р-27). Знаменатель — наступившие плановые приёмы периода
(принято + пропущено осознанно + пропущено без отметки); числитель — принятые в окне; приёмы
«по потребности» исключены — назначенного времени нет, сравнивать не с чем. НАП-2 сюда не
примешивается: он определяет «вовремя» для срабатывания будильника, где опаздывает приложение,
а не человек. Если в периоде нет наступивших плановых приёмов (профиль только «по потребности»
или период пуст), плитка скрывается целиком — измерять нечего (Р-33). Доля меньше процента
показывается словами «< 1 %»: «0 %» при состоявшихся приёмах — ложь. Реализовано
(`core-domain/.../history/OnTimeRule.kt` — `OnTimeRule.TwoHours`, `OnTimeShare.Value(onTime, due)`
и `Absent`; `app/di/HistoryModule.kt` подставляет окно; SKL-105).

Строка вывода — единственное место, где приложение делает обобщение за человека; формулировка
описательная, без совета (П-4); при отсутствии явного лидера скрывается. Разбивка «По лекарствам»:
полоса — доля принятого, одним цветом во всех строках; строка с низкой долей называет себя
подписью — процент набран сильнее и темнее остальных, а цветом доля не называется вовсе
(`12-design.md` §2.1: акцент не маркирует отрицательное). Данных за месяц нет —
плитки показывают прочерки, календарь пуст, разбивка и вывод скрыты. Чужой профиль — история
активного профиля, отметки владельца подписываются «отметили вы», индикация профиля обязательна
(ПРФ-12).

**Отчёт врачу** — локальный PDF без сети: A4 книжной ориентации, шапка с именем профиля и
периодом, сводка (доля принятого, принято вовремя, дни без пропусков, пропуски), разбивка по
лекарствам с датами пропусков, разделёнными на «отмечен человеком» и «без отметки». Отчёт
строится по одному профилю и содержит его имя (ПРФ-23). Оговорка «не является медицинским
документом» — на каждой странице. Имя файла `sklyanka-report-ГГГГ-ММ.pdf` по месяцу начала
периода, кириллицы в имени нет. Передача только системными средствами: «Передать» открывает
системный обмен, «Сохранить» — выбор места; просмотрщика нет.

Шторка отчёта: модальная шапка «Отмена» (после успеха — «Готово») и название; сообщение исхода
баннером первым, если оно есть; чипы периода «Этот месяц» (по умолчанию), «Прошлый месяц»,
«Последние 3 месяца», «Другой период»; карточка состава «Профиль / Период / Принято / Формат»;
тихое пояснение «Отчёт содержит медицинские данные и передаётся в открытом виде.»; действия
«Передать» и «Сохранить» одной формы, равные половины, при крупном шрифте — столбик. Ручки и
жеста «потянуть вниз» нет; закрывают «Отмена», системная «Назад» и тап по затемнению, все три без
передачи. Успех заменяет содержимое шторки целиком: «Отчёт сформирован», «Передан» либо
«Сохранён», галочка; «Передан» означает «отдан системному обмену» и не обещает доставку (П-7).
Отмена системного диалога и ошибка показываются первым элементом, содержимое остаётся, повтор
возможен сразу; текст ошибки называет действие; баннера об исходе на «Истории» нет.

Границы «Другого периода»: «С» — любая прошедшая дата, нижней границы нет, будущее недоступно;
«По» — не раньше «С» и не позже сегодня, недоступные дни приглушены; «С» позже текущего «По» не
запрещается — «По» подтягивается; «С» = «По» допустимо, период печатается одной датой; отмена
диалога значение не меняет, очистки нет — обе даты обязательны; в пределах открытой шторки
значения сохраняются, при новом открытии начинаются с умолчаний. Смена пресета или подтверждение
дат пересобирает состав сразу и сбрасывает сообщение исхода; отчёт не привязан к месяцу,
открытому на «Истории». Пустой период: строки профиля, периода и формата остаются, вместо
«Принято» — «За период нет ни одной записи о приёме». Формат периода в документе: несколько
месяцев — полными датами на обоих концах, внутри одного месяца — «1 — 30 сентября 2026», один
день — одной датой; начало периода печатается ресурсом языка.

### 5.7 Проверка напоминаний

Экран — единый ответ человеку, который пришёл, когда напоминания не приходят: что не так → что
делать → когда было последнее и когда следующее. Технические сведения не показываются (НАП-37);
кнопок «Проверить сейчас» и «Повторить проверку» нет.

### 5.8 Пустые состояния, загрузка, доступность

Пустые состояния есть: «Сегодня» первого запуска и профиля без активных лекарств (редукция знака
одной краской, «Пока ничего не запланировано», пояснение и кнопка «Добавить лекарство»), список
лекарств без активных, пустой архив (без действия). Экран «пусто» показывается, когда у активного
профиля нет **ни одного активного лекарства**; если лекарства есть, а приёмов на сегодня нет,
показывается тихая строка — призыв завести первое лекарство человеку, у которого лекарства
заведены, читается как потеря данных.

Состояний «загрузка» и «ошибка» на экранах нет намеренно: данные локальные, экран рисуется сразу;
отказ чтения локальной базы — аварийная ситуация, а не экранное состояние. Служебные флаги
занятости есть у списка лекарств, архива и переноса; отказы выражаются баннерами и подписями на
месте действия — исход переноса, причина отказа удаления профиля, нарушение валидации формы.

| AC-41 | Все интерактивные элементы — не меньше 44 dp: строки «Исправить» и «Пройти настройку заново», кнопки проверки доставки, «Понятно», «Сообщить о проблеме», «Отправить отчёт», «Повторить», «Отмена». Визуальный размер может быть меньше — цель расширяется невидимо |
| AC-42 | При крупном системном шрифте до 200 % ни один текст не обрезается и не рвётся по буквам: строки разрешений растут по высоте, действие уходит под текст, карточки и кнопки растут; секция «Сообщить о проблеме» и шторка остаются достижимыми, ничего не перекрывается |
| AC-43 | Смысл не только цветом: статус приёма, доставки и разрешения всегда назван словом или числом — «не выдано» / «проверьте вручную», «вовремя» / «опоздание», «Всё в порядке» / текст причины. Слово состояния стоит видимой строкой под названием, перед последствием; оба состояния одинаково приглушены цветом — различаются слово и маркер |
| AC-44 | Минимальный текст 12 px; контраст пар — из `12-design.md`; приглушённый жёлтый не используется. Строка-действие не несёт смысла одной иконкой: у неё подпись словами |
| AC-45 | Порядок обхода чтения с экрана совпадает с визуальным; у иконочных кнопок есть описание; статусная строка и баннер читаются как единое сообщение — заголовок плюс пояснение; шеврон в подписи действия не объявляется |

Масштаб шрифта свободный до 200 %, кроме ступени Display — потолок 130 %, применяется только к
полноэкранному напоминанию. Действие уходит под текст компонентом стековой раскладки с порогом по
измеренной ширине. Декоративные элементы — галочка успеха отчёта, значок «›» — чтению с экрана не
объявляются: исход называют слова. Системная тёмная тема не поддерживается; тёмная поверхность
есть только у полноэкранного напоминания и карточки самопроверки.

## 6. Профили

### 6.1 Модель, разделение, профиль владельца

| Код | Правило |
|---|---|
| ПРФ-1 | Профиль — владелец набора лекарств: `id`, `name`, `color`, `is_self`, `mirror_reminders`; каждое лекарство принадлежит ровно одному профилю |
| ПРФ-2 | Переключение жёсткое, без общего списка: приложение всегда показывает приёмы ровно одного профиля. Общего экрана «все приёмы всех профилей» не существует и не появится (П-2) |
| ПРФ-3 | Целевой сценарий — присмотр за приёмом ребёнка или пожилого родственника со своего телефона, а не несколько независимых учётных записей. Профилей немного, владелец телефона один, аутентификации между профилями нет, переключения частые — главная опасность в том, что человек забывает, в каком профиле находится |
| ПРФ-4 | Смешивание запрещено на уровне данных и запросов, а не только экрана: любая выборка параметризована профилем (ПР-10) |
| ПРФ-23 | История показывает историю ровно одного — активного — профиля; сводной истории по всем профилям нет. Отчёт врачу формируется по одному профилю и содержит его имя |
| ПРФ-24 | Все счётчики и производные показатели — приверженность, дни без пропусков, разбивка по лекарствам, остаток, предупреждение о покупке — считаются в границах одного профиля |
| ПРФ-25 | Профиль владельца один, создаётся при первом запуске автоматически, до всякого онбординга, и существует всегда: данные не могут оказаться без владельца |
| ПРФ-26 | Особенности профиля владельца: напоминания планируются всегда независимо от флага дублирования, сам флаг для него смысла не имеет и в интерфейсе не показывается; индикация чужого профиля не показывается; не удаляется; используется как `actor_profile_id` при отметке чужих приёмов с этого телефона; в настройках показан первым с подписью «Мои лекарства» |
| ПРФ-27 | Имя и цвет профиля владельца редактируются: имя попадает в отчёт врачу и в файл переноса, цвет выбирается из той же закрытой палитры. `[не реализовано]` Экрана редактирования нет |
| ПРФ-31 | Профилей не более пяти: список в настройках обозрим, палитра различима. `[не реализовано]` Проверки лимита нет ни в домене, ни в экранах |

Активный профиль хранится в постоянных настройках приложения
(`data/prefs/ActiveProfileDataStore.kt`), а не в состоянии навигации и не в памяти процесса; при
чтении проверяется существование профиля, и при его отсутствии приложение возвращается к профилю
владельца с записью в журнале. Переключение — тап по строке профиля в настройках
(`domain/profile/SwitchProfileUseCase.kt`).

### 6.2 Дублирование напоминаний

| Код | Правило |
|---|---|
| ПРФ-5 | Флаг `mirror_reminders` отвечает на один вопрос: должен ли телефон владельца звонить, когда наступает время приёма **чужого** профиля |
| ПРФ-6 | Планировщик берёт приёмы профиля владельца всегда; приёмы прочих профилей — тогда и только тогда, когда флаг включён. Активный профиль на состав будильников не влияет (НАП-12); переключение флага — событие перепланирования. Профиль без дублирования существует полноценно: приёмы генерируются, переводятся в «пропущено» общим правилом, попадают в историю — не дублируется только напоминание, а не учёт |
| ПРФ-7 | Настройки показывают состояние флага прямо в строке профиля: «Мама · 4 лекарства · напоминания дублируются мне» — формулировка сообщает, чей телефон зазвонит |
| ПРФ-8 | Напоминание чужого профиля, пришедшее по дублированию, несёт те же визуальные отличия, что и экран чужого профиля: человек, разбуженный ночью, должен с первого взгляда понимать, чей это приём |
| ПРФ-9 | Момент, в который задаётся вопрос о дублировании, — мастер добавления профиля с объяснением. `[не реализовано]` Экрана добавления профиля нет; до появления мастера строки «Добавить профиль» на экране настроек нет вовсе (SKL-105). Значение флага по умолчанию — включено (Р-29); в коде создание профиля требует флаг явным параметром |

### 6.3 Индикация чужого профиля

Цена ошибки — отметка чужого приёма как своего: она искажает сразу две истории и обнаруживается
поздно или никогда, а отчёт врачу после неё становится ложным. Единственный признак человек
перестает замечать, поэтому индикация делается избыточной намеренно.

| Код | Правило |
|---|---|
| ПРФ-10 | Индикация чужого профиля избыточна намеренно |
| ПРФ-11 | Все шесть отличий обязательны и показываются одновременно, когда активен профиль не владельца: (1) цветная полоса вверху экрана во всю ширину; (2) подкрашенная шапка в тон цвета профиля; (3) надпись «Профиль · Имя» над заголовком; (4) баннер «Это не ваши приёмы. Отметки сохранятся в профиль „Имя“»; (5) акцентный цвет действий меняется на цвет профиля; (6) подпись «отметили вы» в истории |
| ПРФ-12 | Отличия 1–5 действуют на всех экранах в контексте профиля: список лекарств, карточка лекарства, архив, история, форма нового лекарства. Экран, на котором индикация исчезает, — дыра в защите |
| ПРФ-13 | Баннер не скрывается и не сворачивается; называет профиль по имени и говорит, куда попадёт отметка |
| ПРФ-14 | Подпись «отметили вы» опирается на `actor_profile_id` и показывается, когда отметку поставил не профиль приёма; в истории своего профиля не появляется |
| ПРФ-15 | Цвет профиля обязан оставаться различимым и контрастным: он используется и как фон шапки, и как цвет акцентных действий. Палитра — ограниченный набор из дизайн-системы, а не произвольный выбор цвета |
| ПРФ-16 | Профилю владельца дополнительной индикации не добавляется: отсутствие индикации — само по себе сигнал |

Индикация — одна обёртка вокруг корня приложения (`app/ProfileChrome.kt`), все шесть признаков
реализованы. `[расхождение]` Индикации нет там, где корень не обёрнут: экран надёжности при входе
из маршрута запуска, заставка и отдельные `Activity` — напоминание, диагностика, самопроверка.
Карточка напоминания несёт подпись профиля отдельным элементом (НАП-29); диагностика и экран
надёжности — `[не реализовано]` по ПРФ-12.

### 6.4 Переключение и удаление

| Код | Правило и факт |
|---|---|
| ПРФ-17 | Активный профиль — состояние приложения, а не экрана: хранится в постоянных настройках, поле хранит идентификатор профиля |
| ПРФ-18 | При перезапуске приложение открывается в профиле, активном на момент выхода; автоматического возврата к своему профилю нет — защиту обеспечивает индикация, а не автосброс |
| ПРФ-19 | Переключение выполняется из настроек, из списка профилей. Быстрого переключателя в шапке «Сегодня» нет: в шапке индикатор, но не одно нажатие до смены контекста; переключение — осознанное действие |
| ПРФ-20 | Напоминание всегда открывается в профиле того приёма, о котором напоминает, независимо от активного профиля. `[расхождение]` Карточка — отдельная `Activity` вне корневого стека: отметка пишется в профиль приёма, но активный профиль приложения не переключается |
| ПРФ-21 | Переключение, вызванное открытием напоминания, видно и обратимо: после отметки или закрытия карточки приложение остаётся в профиле напоминания и показывает его индикацию. Тихий возврат в прежний профиль запрещён |
| ПРФ-22 | `[снято Р-3]` Отметка с часов записывалась в профиль приёма и не меняла активный профиль телефона |
| ПРФ-28 | Профиль владельца удалить нельзя: сценарий удаления отвечает отказом, запрос удаления ограничен записями без `is_self` |
| ПРФ-29 | Удаление чужого профиля каскадное: одной транзакцией удаляются профиль, все его лекарства — активные и архивные — и вся история приёмов; отложенные срабатывания уходят вместе с приёмами. Перед удалением человек видит числа потерь и предупреждение, предлагается сохранить файл переноса, подтверждение — словом «Удалить». Пути назад нет: история не сохраняется обезличенной и не архивируется; промежуточного «скрытия» профиля не существует, фактическое удаление данных возможно только удалением профиля или режимом «заменить всё». Факт: отдельный экран удаления с числами потерь (лекарства всего и в архиве, записи истории), предупреждением, предложением выгрузить файл и словом-подтверждением; стирание одной транзакцией в порядке приёмы → лекарства → профиль (`data/repository/RoomProfileEraser.kt`) |
| ПРФ-30 | Удаление профиля — событие перепланирования, будильники его приёмов снимаются немедленно: напоминание о приёме профиля, которого уже нет, — худший из исходов. Факт: `PROFILE_SET_CHANGED` после стирания |
| ПРФ-31 | Если удаляемый профиль был активным, приложение переключается в профиль владельца и показывает это явно. `[расхождение]` Переключение выполняется при **любом** удалении, а не только активного (`domain/profile/DeleteProfileUseCase.kt`) |

## 7. Перенос данных

### 7.1 Назначение и формат файла

| Код | Правило |
|---|---|
| ПЕР-1 | Перенос — единственный способ переселить историю на другое устройство и единственная резервная копия. Сети приложение не требует, облака нет: файл остаётся у человека и никуда не отправляется (П-3, П-5) |
| ПЕР-2 | Формат — один файл `sklyanka-ГГГГ-ММ-ДД.json`; не архив, не набор файлов, не база целиком |
| ПЕР-3 | Содержимое: лекарства, архив, расписания, история приёмов, профили, настройки. Чипы состава на экране приведены к этому списку: чипа «звуки» нет, чип «настройки» есть |
| ПЕР-4 | Экран показывает дату последней выгрузки — без напоминаний и давления, просто факт: человек должен видеть, насколько устарела его единственная резервная копия. До первой выгрузки строка скрыта |
| ПЕР-5 | Файл — один объект JSON в UTF-8. Обязательные разделы: `format` и `format_version`; `exported_at` и `app` (версия, код версии, платформа); `counts` — сводка для экрана загрузки (профили, лекарства, архив, приёмы); `profiles`; `medications`; `intakes`; `settings` |
| ПЕР-6 | `format` — постоянная строка-опознаватель `sklyanka-export`; файл без неё не считается выгрузкой, даже если это корректный JSON |
| ПЕР-7 | `format_version` — целое число, начиная с 1; повышается при любом несовместимом изменении схемы. Формат заморожен до первой публичной сборки |
| ПЕР-8 | Все моменты времени — строки ISO 8601 со смещением; даты без времени — «ГГГГ-ММ-ДД». Смещение сохраняется, чтобы история, снятая в одном поясе, читалась корректно в другом |
| ПЕР-9 | Идентификаторы в файле — исходные идентификаторы устройства-источника; на приёмнике они не считаются глобально уникальными и при слиянии перевыдаются, а внутри файла служат только для связи разделов |
| ПЕР-10 | Архив — не отдельный раздел, а состояние лекарства: записи с непустыми `archived_at` и `archive_reason`. Удаление — тоже состояние: непустой `deleted_at` переносится вместе с записью. «Заменить всё» не воскрешает удалённые лекарства — состояние читается из файла как есть; при слиянии удалённая запись добавляется удалённой и остаётся скрытой. Физически удалённых записей в файле не бывает |
| ПЕР-11 | Расписание лежит внутри записи лекарства, а не отдельным разделом: оно не имеет смысла в отрыве от лекарства и не переиспользуется |
| ПЕР-12 | Настройки переносятся как значения, а не как системные ссылки. Ссылка на системный сигнал чужого устройства может не разрешиться: загрузка не прерывается, значение падает на умолчание, приложение сообщает об этом в отчёте о загрузке |
| ПЕР-13 | Диагностический журнал срабатываний в файл не попадает: он привязан к устройству и прошивке и на новом устройстве не значит ничего |

Фактический состав (`data/transfer/TransferFileDto.kt`): запись лекарства несёт все поля модели,
включая `package_size` (опускается, если не задан), `deleted_at`, `archived_at`, `archive_reason`;
запись приёма — `scheduled_at`, `status`, `acted_at`, `source`, `actor_profile_id`. У
автоматического пропуска `acted_at` — момент закрытия окна, то есть полночь следующих суток:
иначе нарушался бы ИНВ-10. Раздел настроек несёт сигнал напоминания, признак настойчивого
повтора, интервал откладывания, «тихие часы» и настройки часов. `[расхождение]` Поля «тихих
часов» и часов остались как наследие отложенных и снятых функций (§8) — продуктового состояния
за ними нет, но формат заморожен и без повышения версии не меняется. Тумблер лекарства
`mirror_to_watch` в файл **не пишется** — `[снято Р-3]`, поле подлежит удалению из модели.

### 7.2 Режимы загрузки и слияние

| Код | Правило |
|---|---|
| ПЕР-14 | Режимов ровно два: «Добавить к текущим» — по умолчанию, подпись «Совпадения по названию и дозировке будут показаны отдельно»; «Заменить всё» — подпись «Текущие данные на этом устройстве будут стёрты» |
| ПЕР-15 | «Добавить», по шагам: выбор файла системным выбором → чтение и проверка (опознаватель, версия, целостность), ничего ещё не применяется → сводка из `counts` и `exported_at` → сопоставление профилей, затем внутри каждого профиля поиск совпадений лекарств → совпадения отдельным списком для ручного решения, по одному решению на совпадение, несовпавшие добавляются без вопросов → подтверждение и применение одной транзакцией → отчёт: сколько профилей, лекарств и записей истории добавлено, сколько совпадений разрешено и как, что не удалось перенести |
| ПЕР-16 | «Заменить всё»: шаги 1–3 те же → явное предупреждение с перечислением стираемого в числах и подтверждение отдельным осознанным действием, не одним нажатием подряд с «Выбрать файл» → страховочная выгрузка текущих данных во внутренний файл с сообщением, где он лежит → стирание и применение целиком одной транзакцией, идентификаторы переносятся как есть → активным становится профиль владельца из файла → отчёт и экран настройки разрешений. Факт: копия пишется только в режиме замены, до стирания, под постоянным именем `sklyanka-before-replace.json` во внутреннем хранилище, недоступна другим приложениям и перезаписывается при следующей замене; срока хранения и интерфейса «Вернуть как было» нет `[не реализовано]`. Экран подтверждения показывает две колонки чисел — «сейчас на устройстве» и «будет из файла» — и требует слова «Заменить» |
| ПЕР-17 | Загрузка не запускается в фоне и не переживает выход с экрана: это разовая операция под присмотром. Признак идущей загрузки переживает гибель процесса, и при следующем запуске приложение сообщает, что загрузка не состоялась |
| ПЕР-18 | После любой загрузки выполняется полное перепланирование напоминаний (НАП-11): состав приёмов изменился целиком |
| ПЕР-19 | Профили сопоставляются до лекарств: профиль владельца из файла — с профилем владельца на устройстве, их всегда по одному; прочие — по нормализованному имени, несовпавшие добавляются новыми с новыми идентификаторами; `mirror_reminders` и `color` у существующего профиля не перетираются — настройки устройства принадлежат устройству |
| ПЕР-20 | Два лекарства считаются одним и тем же, если совпадают нормализованное название и дозировка препарата в пределах одного сопоставленного профиля. Нормализация названия: обрезка пробелов, схлопывание внутренних пробелов, нижний регистр, «ё» → «е». Дозировка — пара `strength` + `strength_unit`, а не доза на один приём. Остальное — форма, расписание, период, остаток — на совпадение не влияет и выносится в карточку решения как различия |
| ПЕР-21 | Четыре решения по каждому совпадению: «Оставить моё» — запись устройства не меняется, приёмы из файла привязываются к ней; «Взять из файла» — поля заменяются значениями из файла, приёмы привязываются к той же записи; «Добавить отдельно» — создаётся второе лекарство с новым идентификатором, приёмы к новой записи; «Не загружать» — запись устройства не меняется, приёмы из файла отбрасываются |
| ПЕР-22 | Решение применяется к одному совпадению; массового «применить ко всем» нет — здесь человек принимает решения о своих медицинских данных, скорость не ценность. Кнопка «Не загружать ничего из совпавших» допустима как выход из длинного списка |
| ПЕР-23 | Дубликаты истории: приёмы, совпавшие по паре «лекарство + `scheduled_at`», не удваиваются. Приоритет — записи с определённым исходом («принято» или «пропущено осознанно») над «ожидается» и «пропущено без отметки»; при равенстве — записи с более ранним `acted_at`. Остаток упаковки при слиянии по истории не пересчитывается: берётся значение принятой записи лекарства |

### 7.3 Что не переносится, целостность, приватность

| Код | Правило |
|---|---|
| ПЕР-24 | Разрешения и автозапуск файлом не переносятся: они принадлежат системе, а не приложению |
| ПЕР-25 | После загрузки на новом устройстве открывается тот же экран настройки надёжности, что и в онбординге, включая самопроверку доставки: человек, перенёсший данные, в том же положении, что поставивший приложение впервые — расписание есть, гарантии доставки нет |
| ПЕР-26 | Также не переносятся идентификаторы каналов уведомлений и диагностический журнал (ПЕР-13). `[снято Р-3]` Подключение часов и выданные права |
| ПЕР-27 | Атомарность: загрузка применяется целиком или не применяется вовсе; все записи в одной транзакции хранилища, при любой ошибке состояние откатывается к исходному. Частично применённая загрузка недопустима |
| ПЕР-28 | Битый файл — не читается как JSON, нет опознавателя, опознаватель чужой, отсутствуют обязательные разделы, нарушены связи между разделами. Реакция: ничего не применяется, сообщение «Файл не похож на выгрузку Склянки» с техническим пояснением одной строкой. Приложение не пытается «спасти что получится»: частичное восстановление медицинских данных хуже их отсутствия |
| ПЕР-29 | Файл от более новой версии отклоняется целиком: ничего не применяется, сообщение «Файл создан более новой версией Склянки. Обновите приложение». Чтение незнакомой схемы запрещено |
| ПЕР-30 | Файл от более старой версии читается через миграцию схемы формата, человек предупреждается одной строкой; совместимость снизу поддерживается для всех выпущенных версий. `[расхождение]` Цепочка миграций формата пуста — выпущена только первая версия (`data/transfer/TransferFormatMigrations.kt:45`) |
| ПЕР-31 | Нехватка места или прерывание: проверка свободного места до начала записи; при прерывании незавершённая транзакция откатывается хранилищем, при следующем запуске приложение в исходном состоянии и сообщает, что загрузка не состоялась. Факт: запас места — двукратный размер записываемого |
| ПЕР-32 | Ошибка при выгрузке: файл записывается во временное имя и передаётся в целевое место только после успешной полной записи; при срыве недописанный документ удаляется. Наполовину записанный файл не должен выглядеть как готовая резервная копия |
| ПЕР-33 | Файл содержит медицинские данные: названия лекарств, дозы, расписание и историю за всё время; диагноз по ним восстанавливается без усилий. Файл не шифруется и ничем не защищён — пароля нет |
| ПЕР-34 | Предупреждения при выгрузке: до сохранения, рядом с кнопкой, — файл содержит названия, дозы и историю, не зашифрован, обращаться как с медицинским документом; о месте сохранения — приложение отдаёт файл системному диалогу и не контролирует, куда он попадёт, а папка, синхронизируемая с облаком, унесёт данные в облако, и это должен быть осознанный выбор. В самом файле предупреждений нет |
| ПЕР-35 | Экран переноса сам формулирует принцип, а не прячет его в мелкий шрифт: «Один файл со всеми лекарствами, расписаниями и историей. Облака нет — файл остаётся у вас» |
| ПЕР-36 | Приложение не ведёт учёта, куда человек сохранил файл, и не хранит копий, кроме страховочной выгрузки перед заменой всего; копия лежит во внутреннем хранилище, недоступна другим приложениям и перезаписывается при следующей замене |
| ПЕР-37 | `[снято Р-4]` Согласие на аналитику файлом не переносилось: полей согласия в формате нет и не будет |

Выгрузка одного профиля вместо всех не предусмотрена: файл всегда содержит все профили.
