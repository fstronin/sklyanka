# Склянка — план реализации

Версия 1.0 · 8 октября 2026. Порядок исполнения фаз A–D (`PLAN.md` §3, `docs/v2/04-roadmap.md` §2).
Единица работы — задача SKL-NN из реестра `PLAN.md` §4; статусы живут только там.
Разработку исполняют агенты ИИ; узкие места — приёмка заказчика (5–10 ч/нед), живые
устройства и внешние ожидания (ревью Huawei, модерации), а не объём кода.

## 0. Путь до MVP (текущая цель — Р-51)

Цель — бесплатное ядро, стабильно работающее на телефоне владельца. Платного контура, магазинов
и измерения в MVP нет. Состав: фаза A целиком плюс срез B — онбординг надёжности (SKL-112)
и релизная сборка (keystore по Р-50, версии по Р-26).

| Волна | Задачи | Почему так |
|---|---|---|
| M1 | SKL-108 ∥ SKL-94 | CI и меры сохранности данных: независимые модули (`.github` ∥ `core-data`/`app`), можно параллельно |
| M2 | SKL-105 | визуальные дефекты и единая шапка: экраны стабилизируются до поведенческих правок |
| M3 | SKL-126, SKL-127, SKL-128 | поведенческие расхождения (Р-45, Р-46, Р-44) — **до** финального пересъёма эталонов |
| M4 | SKL-109 | палитра Р-20 и пересъём эталонов один раз, на финальных экранах |
| M5 | SKL-112 | онбординг надёжности: после него ручной чек-лист гоняется **один раз**, с финальным онбордингом |
| M6 | keystore (Р-50) и версии (Р-26) — срез SKL-114 | релизная сборка, которую ставим на телефон; магазинные кадры и листинг сюда не входят |
| M7 | SKL-110 | единый ручной чек-лист на Pura 80 Ultra — **по релизной сборке**, а не по debug |
| M8 | личный прогон владельца | 7 суток пользования сборкой без пропущенных напоминаний и потерь данных |

**Гейт MVP:** `verifyAll` зелёный в CI; нет скрытых, заглушённых и лгущих входов; данные целы;
дефекты и расхождения закрыты; палитра применена; чек-лист пройден; сборка стоит на телефоне
и отработала 7 суток.

**После MVP** (по решению владельца): SKL-113 и SKL-114 (кадры и листинг), SKL-115, SKL-120,
SKL-130; затем фаза C (SKL-117–122) и фаза D (SKL-103, 123, 124, 129, 131).

## 1. Правила исполнения

1. **TDD**: падающий тест → код → рефакторинг (скиллы `.claude/skills/`). Приёмочные
   сценарии после SKL-111 читаются из `acceptance/src/main/resources/features/`.
2. **Конец задачи**: `verifyAll` зелёный + коммит (Conventional Commits, `feat(SKL-NN): …`)
   + статус в `PLAN.md` §4. Задача без зелёного `verifyAll` не закрыта.
3. **Экранные задачи**: эталоны Roborazzi + кадры эмулятора (`tools/emulator/run-ui.sh`)
   + локализационная матрица ×6; всё прошивко-зависимое — строками чек-листа SKL-110,
   а не «на проверке» в пустоте.
4. **Параллельность**: агенты ведут непересекающиеся срезы; общие файлы (`core-ui/token/`,
   эталоны, `feature-settings`) — строго последовательно по волнам ниже. Конфликт по
   эталонам дороже выгоды от параллели.
5. **Гейт фазы закрыт → открываем следующую.** Не закрыт — фаза не начинается, кроме
   задач, помеченных параллельными.
6. **Точки контакта заказчика** планируются заранее и пакетом: ревью кадров (≈30 мин),
   сеансы на Huawei по чек-листу (2–3 сеанса × 2 ч), консольные действия (товары,
   тестовые ID), юридические и страницные действия.

### Карточки задач

**SKL-106 · Вырезание мёртвого груза и лжи.**
Шаги: (1) аналитический контур по списку Р-4 (порт, 16 событий, гейт согласия, хранилище
согласия, `core-analytics`, экран согласия, строка настроек и её строки ×6, события витрины);
(2) часовой шов по списку Р-3 (`WatchGateway`/`NoWatchGateway`, источник `WATCH`, чтение/запись
`mirror_to_watch`, `ToggleWatchMirrorUseCase`, watchMirror на карточке, `OpenWatchSetup`,
`UnpairedWatchLinkReader`, сценарии ЧАС-*); **не трогать** `SetMirrorRemindersUseCase`
и `Profile.mirrorReminders` — профильное зеркалирование, не шов; (3) лже-отчёт
(`StubDeveloperReportSender`, кнопка и шторка) по П-7; (4) выгрузка журнала CSV — служебный
вход на «Проверке напоминаний» через SAF поверх `ExportReminderJournalUseCase`;
(5) приёмочные сценарии удалённых функций — в архив/удаление; (6) пересъём затронутых эталонов.
DoD: grep по `WatchGateway|NoOpAnalytics|AnalyticsEvent|StubDeveloperReportSender` в продуктовых
модулях пуст; в сборке нет входа, который лжёт или обещает отсутствующее; `verifyAll` зелёный.

**SKL-107 · Целостность данных.**
Шаги: ИНВ-3 (неизменяемость `Intake.profile_id`) — доменная проверка на всех путях записи
приёма плюс тест (миграцию схемы не делаем: дорога, обосновать в task.md); ИНВ-14/15/18 —
вызов из продуктивных путей отметки и переноса, не только из тестов; ИНВ-10/11 — проверка
при обычной записи, а не только в `ValidateSnapshot`; явный `PRAGMA foreign_keys` на открытии
базы с тестом нарушения. DoD: тест на каждый инвариант, включая негативный; `verifyAll`.

**SKL-108 · CI.** Восстановить воркфлоу из коммита `73617e30` (`.github/workflows/verify.yml`
и `android-test.yml`): `verifyAll` на push/PR, JDK 17, gradle-кэш; instrumented — workflow_dispatch
с KVM-эмулятором. DoD: первый push зелёный в CI.

**SKL-105 · Визуальные дефекты и расхождения.**

**SKL-126 · Единицы дозы и дозировки от формы выпуска (Р-45).**
Шаги: (1) домен — `DoseUnit` расширить до шести значений, производных от формы: таблетка
(`TABLET`), капсула (`CAPSULE`), сироп (`MILLILITRE`), капли (`DROP`), спрей (`SPRAY`),
инъекция (`INJECTION`); значение `DOSE` убрать; соответствие «форма → единица дозы» сделать
явной таблицей. (2) `strength_unit` — закрытый список {мг, мкг, г, мл, МЕ, %} в форме,
свободного ввода единицы нет ни в одном из двух полей. (3) `feature-meds`: форма лекарства
показывает единицу дозы по выбранной форме, поле «дозировка» — выбор из списка; строки ×6
языков (`ru`, `en-US`, `es`, `de`, `zh-CN`, `kk`). (4) Приёмочные сценарии формы лекарства.
Миграция данных не нужна — сборка не опубликована. `[расхождение]` сейчас: код держит четыре
значения (`core-domain/.../medication/DoseUnit.kt`), а форма жёстко пишет `strength_unit = "mg"`.
DoD: в домене нет значения `DOSE`; обе единицы — только из закрытых списков; матрица ×6; `verifyAll` зелёный.

**SKL-127 · Снятие записи «по потребности» (Р-46).**
Шаги: (1) домен — действие «снятие записи»: мягкий признак «снято», списанная доза возвращается,
доменный тест. (2) Данные — в `IntakeRepositoryImpl.undoAtomically` убрать защитный
`require(mode == SCHEDULE && SCHEDULED)`, реализовать снятие записи по потребности; физического
`DELETE` нет — список допустимого `DELETE` в `ADR-0012` п. 5 не расширяется. (3) Журнал операций:
факт снятия без медицинских данных (НФТ-19). (4) UI — в `feature-today` снэкбар «Отменить» для
записи по потребности в том же окне 5 с (`UndoableActionStore.WINDOW`); снятая запись невидима
в истории и остатке, напоминаний не порождает; термины «Снятие записи»/«Снятая запись» (не
«Отмена отметки» — она только за плановыми). (5) Тесты. DoD: приём по потребности снимается
в окне, доза возвращается, `DELETE` не применяется; `verifyAll` зелёный.

**SKL-128 · Установка поверх новой базы (Р-44, ADR-0012 п. 7).**
Шаги: (1) `core-data` — при открытии базы сравнить `PRAGMA user_version` с ожидаемой; если новее,
схему не открывать и данные не трогать. (2) `app` — блокирующий экран «база новее, обновите
приложение»; разрушающая деградация запрещена. (3) Будильники в этом состоянии не создают
отметок и не показывают карточку приёма, а сообщают о необходимости обновления (П-7).
(4) Тест на отказ открытия при завышенном `user_version`. Экраны продукта, кроме блокирующего,
не трогает и идёт параллельно с 126/127. DoD: данные при попытке открытия не изменяются;
`verifyAll` зелёный.

**SKL-130 · Политика конфиденциальности RU+EN (Р-49).**

## 3. Фаза B — бесплатный выпуск

**SKL-112 · Универсальный онбординг надёжности.** Общие шаги (уведомления, точные будильники,
исключение из энергосбережения, закрепление) + вендорные ветки Xiaomi/Samsung/Huawei через
`VendorClassifier`; разрешения: `SCHEDULE_EXACT_ALARM` с запросом у человека как основной путь,
`USE_EXACT_ALARM` — по результату ревью магазина, обязательная деградация полноэкранного
напоминания до heads-up на Android 14+. DoD: тесты на каждый вендорский профиль; кадры веток.

**SKL-113 · Гейт надёжности на матрице.** Документ правила арифметики `outage` (удержание
доставки средой = опоздание, не перерыв) утверждается заказчиком **до** старта прогона;
протокол: 14 суток непрерывно на каждом устройстве матрицы (Huawei Pura 80 Ultra + 1–2
Android заказчика), сбор журнала CSV, расчёт гейта обновлённым скриптом (`collect.sh`
+ правило из документа); порог ≥95 % в окне ±2 мин на каждом устройстве.

**SKL-114 · Релизные материалы.** Кадры магазинов ru-RU с релизной сборки на устройстве
(и матрица ×6 для листинга), `versionCode` монотонный + `versionName` calver (Р-26),
keystore по ответам заказчика (`docs/archive/tasks/SKL-22/keystore.md`).

**SKL-115 · Публикация в AppGallery.** Листинг: категория, описание по формуле Р-25
(без гарантий доставки), страница политики конфиденциальности заказчика, скриншоты,
возрастная метка health; бесплатная публикация физлицом. RuStore — не трогаем (Р-37).

### Гейт B

гейты сборки пересмотрены), клиент IAP (purchase/restore/cancel), экран «Про», витрина в точке
выбора платной функции, деградация «нет связи → доступ сохранён» (П-6), строка «покупка
привязана к магазину» (Р-39); песочница с тестовыми Huawei ID; товары созданы заказчиком
по заявке, одобренной Huawei (Р-37/Р-38).

### Гейт C
Покупка, восстановление и отмена проходят в песочнице AppGallery; ни одна бесплатная функция
не зависит от биллинга; платное обновление опубликовано.

## 5. Фаза D — измерение и рост

**SKL-123 · Спайк офлайн-распознавания упаковки (Р-18).** Набор: 20–30 упаковок (собственные
заказчика + открытые фото); ML Kit Text Recognition на устройстве + локальный реестр ГРЛС;
метрика: доля верно извлечённых название/форма/дозировка на кириллице; go/no-go по результату,
код спайка одноразовый до решения о включении.
Далее: конверсия и отвал по консоли AppGallery и данным биллинга; пересмотр цены/состава (Р-9/Р-16);
разведка international-регионов AppGallery (6 языков готовы); один B2B-разговор; возврат в RuStore
(SKL-124) и возврат ИИ-ввода — только по фактическим числам.

**SKL-129 · Google Play: публикация бесплатного ядра (Р-47).** Открывается при срабатывании
порога расширения каналов (за 90 дней после платного релиза AppGallery: `install→paid ≥ 1,5 %`
и плато установок MoM < 5 % два месяца подряд) и раньше RuStore: канал охвата без монетизации,
ИП не требуется (Р-12). Листинг бесплатного ядра ×6 языков, ссылка на страницу политики
(SKL-130). Идёт перед SKL-124.

**SKL-131 · Сводный ревью порогов фазы D (Р-48).** Одна точка пересмотра — 90-й день после
платного релиза либо 5 000 установок бесплатного ядра, что наступит раньше. Порядок решений:
(1) состав «Про»; (2) цена; (3) каналы (Р-47). Если `install→paid < 1,5 %` — пересматривается
состав, каналы не расширяются, повторный замер через 90 дней. Итог ревью — запись Р-N.
`[не реализовано]` до наступления порога.

## 7. Риски исполнения и откаты

- **Эталоны**: пересъём только в SKL-109 после замерзания экранов; случайный пересъём раньше —
  откатывать коммит пересъёма, а не править экраны под эталон.
- **Переезд features**: при красном `verifyAll` после SKL-111 — вернуть `featuresPath`
  на старый каталог одной настройкой (путь переопределяем), чинить лоадер отдельно.
- **Ревью Huawei заявки**: отказ — повторная подача с правками описания; фаза C не стартует
  без одобрения, но волны A и B от заявки не зависят.
- **Устройства матрицы**: нет второго/третьего устройства — гейт B честно сужается до
  проверенных (Р-25), а не ослабляется.
