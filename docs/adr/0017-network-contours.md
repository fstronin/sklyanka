# ADR-0017 · Сетевые контуры: аналитика по согласию и платёжный контур

| | |
|---|---|
| Статус | принято 01.11.2026 (Р-93) |
| Заменяет | `ADR-0010` п. 1 и п. 5 в части «сеть разрешена ровно вместе с платным контуром» |
| Связано | `ADR-0016` (free — единственная поставляемая сборка), Р-86, Р-94, Р-95, SKL-165 |

## Контекст

До 01.11.2026 сеть в сборке была разрешена единственным способом: вместе с модулем
`billing-appgallery`. Это правило жило в `AnalyticsContourRules` (один контур, одна
обязательная координата, `INTERNET` как разрешение контура) и проверялось задачами
`VerifyMergedManifestTask` и `VerifyDependencyCompositionTask`.

Решение Р-93 вернуло в поставляемую сборку клиентскую аналитику: `INTERNET`, провайдер
MyTracker, согласие отдельным шагом, каталог событий ПМ-26. Решение Р-94 оставило платный
контур непоставляемым. Значит в артефакте может быть **любой** из двух сетевых контуров,
оба сразу (вариант `pro`) или ни одного — правило «сеть = платный контур» перестало быть
верным.

## Решение

1. В `build-logic` вводится понятие **сетевого контура**: данные (модуль, проект, разрешения,
   обязательные координаты), а не код. Контуров два: `ANALYTICS_CONTOUR` (`:core-analytics`,
   `INTERNET`, координата SDK провайдера) и `PAID_CONTOUR` (`:billing-appgallery`, `INTERNET`,
   `com.huawei.hms:iap`).
2. Правило проверки манифеста: разрешение контура допустимо, только если его объявляет
   контур, входящий в артефакт, и ни один модуль вне контуров его не объявляет. Обратная
   сторона тоже обязательна: контур в артефакте без своего разрешения — нарушение.
   Разрешение, объявленное двумя контурами, законно, если оба в артефакте.
3. Безусловные запреты сохраняются: GMS, Firebase, рекламные и чужие аналитические
   координаты, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`, `AD_ID`. Белый список координат
   проверяется для каждой охраняемой группы, а не только для `com.huawei.*`.
4. Логика правил — чистый объект `NetworkContourRules`, проверяемый на заведомых нарушениях
   отдельной задачей, как уже сделано для правил графа модулей. Гейт без образца нарушения —
   обещание, а не гейт.
5. Провайдер аналитики — за портом в домене; приложение не знает MyTracker. Смена провайдера
   не трогает ни экраны, ни use case.

## Последствия

- `free` объявляет `INTERNET` и несёт координату провайдера; `pro` — ещё и клиент магазина.
  Сборка без обоих контуров по-прежнему возможна и не объявляет сеть.
- Согласие на аналитику — часть состояния настроек: без него провайдер не инициализируется,
  событий нет, очередь оставшихся не отправляется и очищается.
- **Поставщик тянет запрещённое.** `com.my.tracker:mytracker-sdk:3.6.0` объявляет
  `play-services-ads-identifier`, `play-services-appset`, `com.android.billingclient`
  (через него — GMS и Firebase) и `installreferrer`. Группы `com.google.android.gms`,
  `com.google.firebase` и `com.android.billingclient` исключены в модуле контура, потому что
  ослаблять правило состава нельзя. Терпимость SDK к их отсутствию проверена по байткоду:
  клиент покупок гасит себя через `Class.forName`, обращения к `AdvertisingIdClient`
  и `AppSet` перехватываются `Throwable`, авто-отслеживание покупок выключено.
  `ACCESS_NETWORK_STATE` и `AD_ID` не объявляются: рекомендация поставщика не выполняется (НФТ-15).
- **Релизная сборка без ключа поставщика отказывает** — ключ (`sklyanka.mytracker.key`
  или `mytracker.key` в `local.properties`) обязателен для `assemble*Release`, но не нужен
  для отладки и `verifyAll`. Ключ — в git не попадает.
  **01.11.2026:** приложение “Склянка” заведено в MyTracker (аккаунт «Стохастика», проект
  «Склянка», валюта RUB, источник — карточка AppGallery), ключ получен и лежит
  в `local.properties`; `MYTRACKER_KEY` попадает в `BuildConfig` модуля.
- **`ACCESS_NETWORK_STATE` принадлежит контуру аналитики (Р-100).** Измерено на устройстве:
  без разрешения SDK зовёт `ConnectivityManager.getActiveNetworkInfo()`, получает
  `SecurityException` и не отправляет события вовсе — пакеты «время в приложении» при этом
  уходят, поэтому дефект незаметен. После объявления разрешения контуром:
  `Events were sent successfully`, очередь SDK пуста. `ACCESS_WIFI_STATE` и `AD_ID`
  остаются запрещёнными всегда.
- Лечение медицинских данных не меняется: события не содержат названий, доз, расписаний,
  идентификаторов профилей (АН-3, НФТ-19).
- Смена провайдера или добавление третьего сетевого контура — новым ADR; это архитектурная
  граница, а не настройка.
