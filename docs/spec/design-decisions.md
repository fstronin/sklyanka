# Журнал дизайн-решений

Журнал ответов дизайна — единый источник «что мы уже решили по дизайну». Ведётся
дополнением: новые решения дописываются, старые **не переписываются и не удаляются**.
Когда вопрос закрыт, здесь появляется запись; в `docs/spec/12-open-questions.md`
(реестр «что открыто») обновляется статус того же `ОВ-N`.

Ссылки: полные формулировки вопросов и варианты — `docs/spec/12-open-questions.md`
(ищи `ОВ-N`); исходники — дизайн-система `sklyanka-design-system.html`, макеты
`design/screens/*.dc.html` / Open Design `screens/*.dc.html`, SPEC.

Формат записи: `### ОВ-N · Вопрос` → `Решение` / `Обоснование` / `Кто` / `Затрагивает`.

## Решения

### ОВ-9 · Тёмная среда
- **Решение:** тёмная среда — `--dark-env #191512`; текст на тёмном `--on-dark #FBF7F1`,
  `--on-dark-muted #C9BFB1`; акцент на тёмном `--accent-dark #C9633D`.
- **Обоснование:** `#241F1B` — цвет текста, а не фон; зафиксировано дизайн-системой v1.0.
- **Кто:** Дизайн (дизайн-система v1.0).
- **Затрагивает:** `docs/spec/08-design-system.md` §4, SKL-05/13/21.

### ОВ-10 · Палитра цветов профиля
- **Решение:** закрытая палитра четырёх токенов: `--profile-1 #B4512F`, `--profile-2 #1F5F6B`,
  `--profile-3 #7A5B2E`, `--profile-4 #6B4A6B`; свой профиль по умолчанию `--profile-1`;
  производные (фон шапки, границы, плашки) — фиксированной формулой от акцента; `color` хранит
  индекс палитры, а не произвольный hex.
- **Обоснование:** произвольный цвет ломает контраст белого текста; автоназначение лишает выбора.
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` §9, `02-data-model.md` §3, экран профиля; SKL-05/15/21.

### ОВ-12 · Цвета статусов приёма
- **Решение:** принято `#1F5F6B`, частично `#6E9FA8`, пропущено `#C9BFB1`; вместе с числом, а не
  только цветом (НФТ-30).
- **Обоснование:** зафиксировано дизайн-системой v1.0.
- **Кто:** Дизайн (дизайн-система v1.0).
- **Затрагивает:** `08-design-system.md` §4, SKL-05/10/18.

### ОВ-17 · Цель нажатия 44 dp
- **Решение:** 44 dp — требование. Визуальный размер мелких элементов (32–38 px) сохраняется,
  область нажатия расширяется прозрачными полями и отрицательными отступами; где области
  накладываются — растёт вёрстка, а не цель.
- **Обоснование:** аудитория 60+; мелкая цель = промах.
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` §3.3, `03-screens.md`.

### ОВ-35 · Просроченный приём
- **Решение:** та же карточка с акцентом `--warning`: подпись «опоздание на N ч», маркер слева,
  позиция в списке не меняется; при переходе в MISSED цвет → `--skipped`, список стабилен.
- **Обоснование:** до конца суток приём остаётся отмечаемым (ОВ-4).
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` §4 (`.intake--overdue`), `03-screens.md`.

### ОВ-37 · Отступления формы нового лекарства (Д-2/Д-3)
- **Решение:** один CTA «Сохранить лекарство» (дубль «Готово» убран); «Режим приёма» стоит до
  блоков времени; условные поля по режиму/форме.
- **Обоснование:** зафиксировано дизайн-системой v1.0.
- **Кто:** Дизайн (дизайн-система v1.0).
- **Затрагивает:** `03-screens.md` (форма), SKL-09.

### ОВ-38 · Поле ввода в состоянии ошибки
- **Решение:** единое состояние: рамка 1,5 px и подпись `--danger` под полем слева, иконка «!»;
  появление при потере фокуса и при сохранении; все подписи + автоскролл к первой.
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` (`--danger`, `.field--error`), SKL-05/09/19/20.

### ОВ-40 · Карточка архивированного и «по потребности» лекарства
- **Решение:** архив — плашка «В архиве с <дата>», кнопка «Вернуть», остаток read-only без
  предупреждения, неделя обрывается днём архивации (дальше штриховка); PRN — без расписания,
  «Не чаще N раз», «Принял сейчас», история точками, «хватит на N дней» не выводится.
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` (`.medcard--archived`, `.medcard--prn`), `03-screens.md`.

### ОВ-41 · Цвет остатка и чужого профиля
- **Решение:** `#8F3E23` (`--warning`) остаётся только за остатком (цвет + иконка + положение).
  Чужой профиль различается формой — постоянная плашка «Профиль: Имя» в шапке каждого экрана, а не цветом.
- **Обоснование:** на экране чужого профиля цветной остаток переставал выделяться.
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` §4, `06-profiles.md` §3, `03-screens.md` (см. ОВ-57).

### ОВ-43 · Пустой архив
- **Решение:** архив пуст целиком — знак, «Архив пока пуст», объяснение; одна группа пуста —
  заголовок скрывается вместе с содержимым.
- **Кто:** Дизайн; формулировки — на утверждение заказчика.
- **Затрагивает:** `03-screens.md` (состояния Archive).

### ОВ-46 · Опечатка в числах карточки
- **Решение:** опечатка в строке расписания — верно «2 приёма в сутки · по 1 таблетке»
  (9 / 2 = 4 дня, как в блоке остатка и `Main.dc.html`).
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md` (доза в примере).

### ОВ-49 · Экран диагностики напоминаний
- **Решение:** отдельный экран. Порядок: разрешения с действием → последнее сработавшее →
  ближайшее → канал → автозапуск → журнал (свёрнутый); внизу «Пробное напоминание» и
  «Выгрузить журнал»; при исправности — блоки 2–3 и «Всё в порядке».
- **Кто:** Дизайн. Зависит от ОВ-48 (точка входа).
- **Затрагивает:** `03-screens.md`, `04-reminders.md` §9, `08-design-system.md`.

### ОВ-63 · «Часы в сети» при кратком разрыве
- **Решение:** последнее устойчивое состояние с гистерезисом (30 с / 5 с) + факт
  «Последняя карточка доставлена в 09:00»; то же для строки в настройках.
- **Кто:** Дизайн + разработка; порог — рабочее умолчание до SKL-17.
- **Затрагивает:** `03-screens.md`, `02-data-model.md` (время последней доставки).

### ОВ-67 · Экраны переноса данных
- **Решение:** разбор совпадений — строки «было/стало» с сегментом «Объединить/Оставить обе/
  Пропустить», «Применить ко всем», по умолчанию «Объединить»; «Заменить всё» — числа потерь +
  ввод слова-подтверждения, кнопка `--danger`.
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md`, `07-data-transfer.md`, `08-design-system.md`.

### ОВ-70 · Порог стекло/плоско
- **Решение:** 90 dp (ниже — плоская, 90 и выше — стеклянная), в dp, а не px.
- **Кто:** Дизайн.
- **Затрагивает:** `08-design-system.md` §7, `03-screens.md`.

### ОВ-81 · Отмена на полноэкранной карточке напоминания
- **Решение:** отмена после каждого действия, включая карточку: карточка закрывается, снэкбар
  «Отменить» показывается на «Сегодня» (4–6 с).
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md` (Reminder), `08-design-system.md` (снэкбар); SKL-30.

### ОВ-82 · Баннер ненадёжности на «Сегодня»
- **Решение:** `.alert` первым в контенте «Сегодня» (под шапкой, над плашкой остатка), со ссылкой
  «Подробнее» в диагностику (ОВ-49). Тексты: «Уведомления выключены — напоминания не придут.
  Включить»; «Напоминания могут опаздывать. Разрешить точные будильники»; «Напоминания сейчас
  не приходят. Проверьте настройки».
  *(Устарело — заменено записью «ОВ-82 · … — уточнение по SKL-29» ниже: одно действие «Настроить»
  ведёт на разрешения; `.alert--warning`/`.alert--danger` не вводятся, «Подробнее» не делается.)*
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md`, `08-design-system.md` (`.alert--warning`, `.alert--danger`); SKL-29.

### ОВ-83 · Форма нового лекарства в режиме «По потребности»
- **Решение:** скрыты «Время приёма» и «Связь с едой»; на месте «Приёмов в сутки» — «Не чаще N раз
  в сутки» (ОВ-36); остаток остаётся; «хватит на N дней» не выводится (ОВ-39).
- **Кто:** Дизайн. Опирается на ОВ-39 (заказчик).
- **Затрагивает:** `03-screens.md`, `02-data-model.md` §3, SKL-09.

### ОВ-84 · Ссылка «Принято N из M» на историю
- **Решение:** строка — ссылка на историю на обоих видах «Сегодня», включая плотный день.
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md`; SKL-31.

### ОВ-85 · Степпер «Приёмов в сутки»
- **Решение:** степпер — вывод, а не ввод: число всегда равно числу строк «Время приёма», +/−
  добавляют/убирают строку; отдельной валидации числа нет.
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md`, SKL-09.

### ОВ-34 · «Сегодня» без приёмов (ждёт заказчика)
- **Решение (рекомендация дизайна):** третий вид — нейтральный знак, «На сегодня приёмов нет»,
  при наличии — «Следующий приём — завтра в 09:00»; отдельно «Все курсы завершены. Загляните
  в архив». Формулировки — заказчику.
- **Затрагивает:** `03-screens.md`.

### ОВ-36 · «не чаще N раз в сутки» (ждёт заказчика)
- **Решение (рекомендация дизайна):** блок «Приёмов в сутки» подменяется тем же степпером с
  подписью «не чаще N раз в сутки»; лимит обязателен для PRN. Допустимая кратность — заказчику.
- **Затрагивает:** `03-screens.md`, `02-data-model.md` §3, SKL-07/09.

### ОВ-69 · Ступени знака (ждёт заказчика)
- **Решение (рекомендация дизайна):** две ступени (стеклянная + плоская, один порог ОВ-70);
  лестница `SklyankaScale.dc.html` — иллюстрация. Состав ресурсов — заказчику.
- **Затрагивает:** `08-design-system.md` §7, SKL-21.

### ОВ-82 · Баннер ненадёжности на «Сегодня» — уточнение по SKL-29
- **Решение:** баннер — существующий `Banner` вида `BannerKind.Warning`; нового вида и новых
  токенов нет. Место — первым в шапке «Сегодня»: сразу под `ScreenHeader`, выше полосы
  прогресса дня и выше плашки остатка, только в дне с приёмами (`Content`). Справа ровно одно
  тихое действие «Настроить», оно ведёт на экран разрешений с `OnboardingSource.TODAY_WARNING`
  (индикатора шагов нет). Ссылка «Подробнее» в диагностику из первой редакции ОВ-82 не
  вводится: контракт `Banner` — «ровно одно тихое действие», а приёмка SKL-29 требует, чтобы
  нажатие возвращало на экран разрешений. Тексты причин совпадают с диагностикой — один отказ
  называется одними словами на обоих экранах: «Напоминания сейчас не приходят: уведомления
  отключены»; «Напоминания могут приходить с опозданием: не выдано право на точные будильники»;
  «Напоминания сейчас не приходят: отключены уведомления и не выдано право на точные будильники».
- **Обоснование:** (1) приёмка важнее первой редакции решения — нажатие ведёт к разрешениям;
  (2) второй ссылки в строке-предупреждении не заводится: два действия превращают её в диалог,
  который человек не читает; (3) §4.6 дизайн-системы уже отводит виду «Предупреждение» случай
  «непройденное разрешение», а причина различается текстом, а не цветом (НФТ-30);
  (4) формулировка `BOTH_OFF` обязана называть обе причины одним сообщением (сценарий приёмки
  «предупреждение называет обе причины»), поэтому она отличается от первой редакции;
  (5) диагностика остаётся доступной из настроек (`ОВ-48`), отдельный вход с «Сегодня» не нужен.
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md` («Сегодня»), `08-design-system.md` §4.6 (пояснение); SKL-29 —
  правка `TDD.md` §3.5 и §4.1: место баннера (первым в шапке), одно действие «Настроить», три
  текста причин вместо двух, ссылки «Подробнее» и вида `.alert--danger` нет.
- **Новые сущности:** нет; `.alert--danger` из ответов 28.09 не вводится.

### ОВ-81 / ОВ-6 · Отмена в коротком окне — уточнение по SKL-30
- **Решение:** отмена показывается новым компонентом системы `Snackbar` (§4.12): текст
  о случившемся и одно тихое действие «Отменить», без значка и тени, на `Surface` с рамкой
  `LineOnSurface`, радиус `Large`, поля 16/12. Снэкбар живёт только на «Сегодня» (в обычном
  и чужом профиле), поверх контента, над нижней панелью: боковые поля 20 dp, отступ до
  панели 12 dp; панель остаётся видимой и нажимаемой. Срок — **5 секунд** (коридор 4–6);
  без действия исчезает сам. Вторая отметка, пока снэкбар виден, заменяет текст и
  перезапускает срок: ячейка одна — «последнее действие». Тексты: «%1$s — приём отмечен
  как принятый» и «%1$s — приём отмечен как пропущенный»; название лекарства — аргумент
  шаблона. Отметка нескольких приёмов одним действием (нижние кнопки карточки напоминания
  на нескольких лекарствах) показывает счётную форму через `plurals`; «Отменить» тогда
  отменяет все приёмы одного действия. После действия на полноэкранной карточке (ОВ-81)
  карточка закрывается, открывается «Сегодня» и показывается тот же снэкбар; «Отложить»
  снэкбара не даёт — отменять нечего.

  **Счётные формы `plurals` (НФТ-44), точно.** «Принято»: one «%1$d приём отмечен как
  принятый», few «%1$d приёма отмечены как принятые», many «%1$d приёмов отмечены как
  принятые», other «%1$d приёма отмечены как принятые». «Пропущено»: one «%1$d приём
  отмечен как пропущенный», few «%1$d приёма отмечены как пропущенные», many «%1$d приёмов
  отмечены как пропущенные», other «%1$d приёма отмечены как пропущенные» (`other`
  обязателен для Android и повторяет конвенцию `strings.xml`).

  **Частичная отметка строки в карточке из нескольких приёмов отмены не получает.** Отметка
  одной строки карточку не закрывает — остаются другие приёмы; карточка остаётся открытой,
  снэкбар не показывается ни на карточке, ни на «Сегодня». Снэкбар получает только действие,
  закрывшее карточку; если её закрыла последняя по счёту отметка строки, снэкбар относится
  к ней, а не к более ранним отметкам. Видимая обратная связь остаётся в самой карточке:
  отмеченная строка исчезает из списка.
- **Обоснование:** (1) 5 с — середина коридора: человек 60+ успевает заметить, а системный
  таймер не выходит за границы 4–6 с при дрожании; (2) одна ячейка вместо очереди — снэкбар
  всегда относится к последнему действию, а очередь предлагала бы отмену устаревшего;
  (3) смысл несут текст и подпись действия, цвет и значок не нужны (НФТ-30); (4) счётная
  форма обязательна для пути напоминания: нижние кнопки отмечают весь слот (НАП-36), и текст
  с одним названием назвал бы одно лекарство из трёх; (5) снэкбар и баннеры не мешают друг
  другу — баннеры постоянные и стоят в шапке, снэкбар временный и внизу над панелью;
  (6) частичную отметку нельзя закрыть карточкой — человека выбросит из недоделанного
  напоминания, а оставшиеся приёмы потеряются; нельзя и показать поверх карточки — это
  второй слой поверх блокировки, а тёмного вида снэкбара нет и §5 не предусматривает третью
  тёмную поверхность. Если практика покажет, что по строкам промахиваются, обратимый вид
  строки карточки — отдельная задача, а не тихий снэкбар на карточке.
- **Кто:** Дизайн; ОВ-6 пересмотрен ведущей сессией (отмена в коротком окне, 28.09.2026).
- **Затрагивает:** `08-design-system.md` §4.12 (компонент `Snackbar`), `03-screens.md`
  («Сегодня» — поведение после отметки, «Сегодня — чужой профиль», «Напоминание» — что
  происходит после действия); SKL-30 — acceptance и TDD: точные тексты, 5 с, замена,
  «только Сегодня», отмена одним действием всех приёмов отметки.
- **Новые сущности:** компонент `Snackbar`; новых токенов нет.

### ОВ-32 / ОВ-84 · Плотный день — уточнение по SKL-31
- **Решение (ОВ-32).** Групповой карточки одновременных приёмов больше нет. Приёмы одного
  времени, которое наступило, показываются отдельными строками: время стоит один раз
  в разделителе ленты — «14:00» с меткой «Сейчас» справа, — под ним подпись группы
  «3 приёма · отметьте по одному», затем обычные карточки приёмов с индивидуальными кнопками
  отметки (см. `03-screens.md`, «Сегодня»). Подпись склоняется через `plurals` по числу
  приёмов, **ожидающих отметки** («2 приёма», «5 приёмов», «21 приём»), и видна вместе
  с кнопкой батча, пока таких приёмов не меньше двух: подпись и кнопка описывают одно
  оставшееся действие и не должны спорить друг с другом. Кнопка «По одному» удаляется,
  механика `expandedGroups`/`ExpandGroup` становится ненужной — строки и есть вид
  по умолчанию. По одной показываются одновременные приёмы и в обычном виде «Сегодня»:
  групповой карточки не остаётся ни в одном из видов, различие видов — только свёртка
  по времени суток. Батч-кнопка есть только у ленты, время которой наступило; у будущих
  приёмов она отмечала бы принятыми то, что ещё не принято.
- **Кнопка батча — два состояния.** Обычное — контурная `SecondaryButton` (§4.3):
  «Отметить оба» / «Отметить все три» / «Отметить все N». Первое нажатие ничего не отмечает:
  кнопка становится `PrimaryButton` — акцентная заливка `Accent` (в чужом профиле акцент
  профиля, ПРФ-11) — и спрашивает «Подтвердить отметку обоих?» / «Подтвердить отметку всех
  трёх?» / «Подтвердить отметку всех N?». Второе нажатие отмечает все ожидающие приёмы
  группы — каждый отдельной записью, остаток списывается по каждому лекарству (ПР-2, ПР-5);
  батч только принимает (`taken`), «Пропустить» батчем не отмечается. Новых токенов
  и компонентов нет: подтверждение — комбинация существующих кнопочных видов, НФТ-30
  выполняется сменой подписи **и** заливки (контурная → акцентная). Кнопка — во всю ширину
  под строками группы; габарит в обоих состояниях один — высота 52 dp и радиус `Large` 16
  (§4.3), иначе смена состояния сдвигала бы строки под пальцем.
- **Сброс подтверждения.** Нажатие вне кнопки (в том числе отметка любой строки), уход
  с экрана (тот же `onScreenLeft`, что закрывает окно отмены, SKL-30) и 10 секунд без
  действия (коридор 8–12) возвращают кнопку к обычному виду молча, ничего не отмечая.
  Прокрутка подтверждение не сбрасывает: рассматривание — не отказ, а заряженное состояние
  ограничено таймером. 10 секунд — время прочитать вопрос при системном шрифте до 200 %
  и решиться; пяти секунд окна «Отменить» для решения мало (там узнают случившееся, здесь
  принимают решение), а без таймера кнопка оставалась бы заряженной незаметно. Подтверждение
  живёт в зрительной части состояния экрана (рядом с `toggledSections`), а не в домене
  и не в локальном состоянии Compose: сброс — решение экрана, а не побочный эффект
  пересборки повестки; вне процесса не переживает.
- **Решение (ОВ-84).** Строка прогресса дня — ссылка на историю на обоих видах «Сегодня»:
  справа в строке подписи стоит тихое действие «История ›» (слово — ресурс, «›» — значок,
  чтением с экрана не объявляется). Цель нажатия — вся строка, не меньше 44 dp; визуально
  подпись не растёт — цель расширяется невидимо (§3.3, ОВ-17). Полоса над подписью остаётся
  неинтерактивной, других изменений в шапке нет. Переход: `TodayIntent.OpenHistory` →
  `TodayNavigation.openHistory`; в `app` история открывается с `HistoryOrigin.TODAY`, возврат
  ведёт на «Сегодня» (из настроек — прежний `HistoryOrigin.SETTINGS`). Когда блока прогресса
  нет (нечего считать), нет и ссылки.
- **Снэкбар SKL-30 — без изменений.** Снэкбар остаётся поверх контента над нижней панелью,
  окно 5 с, одна ячейка «последнее действие». Подтверждение — состояние кнопки, а не второй
  слой, и снэкбару не мешает. После батча снэкбар показывает счётную форму, как и раньше;
  «Отменить» возвращает приёмы, и кнопка батча появляется заново в обычном (не подтверждающем)
  состоянии. Нажатие «Отменить» — нажатие вне кнопки, поэтому им же снимается подтверждение.
- **Доступность.** Состояние подтверждения читается словами: носитель — видимая подпись-вопрос,
  отдельного `contentDescription` у кнопки нет. Переход в подтверждение озвучивается чтением
  с экрана (`LiveRegionMode.Polite` на кнопке), чтобы человек, не различающий заливку, услышал
  вопрос; цвет — второй носитель (НФТ-30/31). Контрасты — из §6.1: `Surface` на `Accent` 5,05,
  `Text` на фоне 15,29. При крупном системном шрифте подписи переносятся, высота кнопки растёт,
  текст не обрезается (§6.3).
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md` («Сегодня» — прогресс-ссылка и ленты, «Сегодня — плотный
  день», «Навигация»); SKL-31 — acceptance и TDD (состояния кнопки, сброс, тексты, маршрут);
  `feature-today` — `TodayIntent.ExpandGroup`, `expandedGroups` и групповая карточка удаляются,
  добавляются подтверждение и `OpenHistory`; тексты — в ресурсы: `group_caption_by_one`
  (`plurals`), `group_confirm_both`, `group_confirm_all_three`, `group_confirm_all_n`,
  `today_history_link`; `group_mark_one_by_one`, `today_now_inline` и `group_medications_separator`
  больше не нужны.
- **Новые сущности:** нет; новых токенов и компонентов не требуется.

### ОВ-86 · Системная «Назад» на экране разрешений
- **Решение:** системная «Назад» — это выход с экрана разрешений, а не завершение приложения.
  Отдельного исхода у неё нет: она делает то же, что видимый выход этого экрана для данной точки
  входа, — идёт тем же путём, что кнопка «Пропустить, настрою позже».
  - **Из баннера «Настроить» на «Сегодня»** (`TODAY_WARNING`): экран закрывается, человек
    возвращается на «Сегодня». Предупреждение остаётся — разрешения по-прежнему не выданы, —
    и вход на экран возможен тем же баннером. Ничего не фиксируется и не переключается.
  - **Из настроек** (`SETTINGS`, `PermissionsActivity`): возврат в «Настройки».
  - **При первом запуске** (`FIRST_LAUNCH`): онбординг прерывается «Пропустить, настрою позже» —
    экран отмечается просмотренным, человек попадает на «Сегодня» с предупреждением, и при
    следующем запуске приложение само онбординг не открывает. Повторный вход — только баннером
    или из настроек, без индикатора шагов; «Назад» на таком входе ведёт туда, откуда пришли.
- **Чем отличается от «Пропустить».** Наблюдаемым исходом — ничем, и это намеренно:
  «Пропустить» называет решение словами, «Назад» — привычный жест; оба означают «настрою позже».
  Альтернативы хуже: завершать приложение по системной кнопке (человек уходит из приложения,
  не увидев ни предупреждения, ни «Сегодня») или оставлять онбординг непройденным и показывать
  его при каждом запуске — то есть получить ту самую жалобу «приложение каждый раз просит
  разрешения», ради которой экран открывается сам только пока не виден (НАП-21). Отдельного
  исхода «назад» у онбординга не заводится.
- **Когда появится приветствие** (ОВ-51) и экран разрешений станет вторым шагом онбординга,
  «Назад» на нём должно вести на приветствие — как шаг назад; на первом шаге онбординга «Назад»
  остаётся «Пропустить». На требование к SKL-14 сегодня это не влияет.
- **Обоснование:** экран разрешений — не ловушка и не модальное окно поверх задачи, а шаг,
  который можно отложить; выход обязан вести к месту входа, а при первом запуске — на
  «Сегодня» с предупреждением: это единственный экран, который объяснит последствия отказа
  и вернёт на настройку.
- **Кто:** Дизайн.
- **Затрагивает:** `03-screens.md` («Разрешения (онбординг)» — правило системной «Назад»),
  `04-reminders.md` §4 (НАП-21); SKL-14, SKL-29.
- **Правка кода (SKL-14 / SKL-29):** `PermissionsRoute` обрабатывает системную «Назад»
  (`BackHandler`) вызовом того же действия, что кнопка «Пропустить» (`viewModel.onSkip()`) —
  тогда все три источника получают правильный возврат без новых параметров;
  `OnboardingViewModel.start()` сбрасывает исход (`exit = null`), иначе повторный вход с тем же
  исходом не закрывает экран (`StateFlow` не эмитит равное значение, `LaunchedEffect(exit)`
  не перезапускается); приёмку дополнить сценариями: «Назад» на первом запуске ведёт
  на «Сегодня» и онбординг больше не открывается сам; «Назад» из баннера возвращает
  на «Сегодня», предупреждение на месте; «Назад» из настроек возвращает в настройки.
- **Новые сущности:** нет.

### ОВ-45 / ОВ-13 · Размер упаковки и «Пополнить» — уточнение по SKL-34
- **Поле формы.** В блоке «Остаток в упаковке» появляется строка **«Размер упаковки»** — сразу
  под строкой «Сейчас есть», выше разделителя и «Напомнить о покупке»: привычное первое число
  блока не двигается, а новое читается вместе с ним («Сейчас есть 9» → «Размер упаковки 60» →
  «9 из 60»). Строка повторяет «Сейчас есть» один в один: компактное числовое поле, справа —
  та же единица измерения из формы выпуска («таблеток», «капсул», «мл», «доз»; ОВ-16). Поле
  **необязательное**: пустое значит «размер не задан»; автоматически из «Сейчас есть» значение
  не подставляется — подставленный знаменатель выдавался бы за измеренный, а поле заведено
  именно затем, чтобы размер знать, а не угадывать (ОВ-45). Подсказка под строкой:
  «Необязательно. Карточка покажет, сколько осталось от упаковки».
- **Ошибка поля — общая ОВ-38:** единственное правило — заполненное значение должно быть больше
  нуля; при нарушении рамка 1,5 dp цветом `--danger`, подпись слева под полем с «!»: «Размер
  упаковки должен быть больше нуля». Появление при потере фокуса и при сохранении, автоскролл
  к первой ошибке (ОВ-38). Если размер заполнен, а «Сейчас есть» пуст, ошибки нет: без остатка
  размер ни на что не влияет, а блок остатка появится, когда появится остаток. Остальное
  в форме — без изменений: один CTA «Сохранить лекарство», «Режим приёма» выше времени (ОВ-37).
- **Карточка — строка «N из M».** Показывается, когда заданы оба числа и N ≤ M: N — `stock_left`,
  M — `package_size`; текст по макету — «9 таблеток из 60» (склонение единицы по N через
  `plurals`, M — числом). Полоса — доля N/M (в макете 9/60 = 15 %), компонент `ProgressBar` §4.7:
  высота 8 dp, радиус `Pill`, дорожка `ProgressTrack`, заполнение `Accent`, а при сработавшем
  пороге покупки — `ProfileForeign` (`--warning`): так нарисован макет, где «хватит на 4 дня»
  уже горит. Полоса всегда сопровождается тем же числом текстом — цвет не единственный носитель
  (НФТ-30, §4.7).
  - **Размер не задан** (старые данные, файл без поля, человек не заполнял): строка
    «осталось N <единиц>» без «из» и без полосы — сегодняшний вид SKL-12; никакого сообщения
    о недостающем размере нет.
  - **Размер меньше остатка (N > M**, например две упаковки): полоса не рисуется — доли больше
    целого не существует, а «N из M» читалось бы как ошибка; показывается то же «осталось N
    <единиц>». Когда остаток опустится до M и ниже, строка снова станет «N из M» с полосой.
    Запрещать N > M формой нельзя: две упаковки — законный запас.
  - **«По потребности»** (ОВ-39, ОВ-40): «N из M» и полоса показываются, если размер задан,
    но предупреждение не выводится — суточный расход для PRN неизвестен, «хватит на N дней»
    нет (ОВ-39); полоса остаётся `Accent`.
  - **Архив** (ОВ-40): остаток read-only без предупреждения — полоса акцентом; решение
    не пересматривается.
- **«Пополнить».** Форма — не диалог и не шторка: строка ввода открывается в самом блоке
  «Остаток», под строкой «N из M» (модальных компонентов дизайн-система не содержит, а одно
  число не стоит отдельного слоя). Поля: число нового остатка (подсказка «Сколько осталось»)
  и единица измерения — та же, что в строке остатка. Действия: «Сохранить» (второстепенная)
  и тихая «Отмена». Валидация: отрицательное значение — ошибка ОВ-38 «Остаток не может быть
  отрицательным»; пустое поле сохранение не выполняет; ноль допустим («кончилось»). Новое
  значение **заменяет** `stock_left` (решение ОВ-13), `package_size` при этом **не меняется**:
  размер упаковки — свойство упаковки и правится только формой «Изменить». Купив упаковку
  другого размера, человек меняет размер там же; строка и полоса пересчитываются. Предупреждение
  о покупке пересчитывается тем же правилом ПР-13 от нового остатка: «хватит на N дней»
  и тревожный цвет гаснут, если запаса стало достаточно, и появляются, если он ниже порога;
  баннер на «Сегодня» — тот же пересчёт, без перезахода.
- **Перенос данных.** В файл добавляется необязательное поле `package_size`: выгрузка пишет его,
  если задано, и опускает, если нет. Файл без поля читается как `null` — визуально это ровно
  состояние «размер не задан»: карточка показывает «осталось N» без полосы и ничего не сообщает;
  размер можно дозаполнить правкой лекарства. Дефолт — `null`, а не копия остатка: выдуманный
  знаменатель врёт полосой. Визуально наблюдаемого отличия «файл без размера» от «размер
  не заполняли» нет и быть не должно — человек не получает предупреждения о том, чего не терял.
- **Кто:** Дизайн; ОВ-45 и ОВ-13 решены ведущей сессией 29.09.2026 (поле `package_size`;
  «Пополнить» — ввод нового числа).
- **Затрагивает:** `03-screens.md` («Новое лекарство», «Карточка лекарства»),
  `02-data-model.md` §3 (поле `package_size`), `07-data-transfer.md` §2 (поле файла); SKL-34.
- **Новые сущности:** нет; полоса — существующий `ProgressBar` §4.7.

### ОВ-15 · Отчёт врачу в PDF — уточнение по SKL-33
- **Решение:** отчёт — локально собранный PDF (A4, книжная ориентация), передаваемый системными
  средствами: «Передать» — системное «Поделиться» (`ACTION_SEND`, `application/pdf`),
  «Сохранить файлом» — системный выбор места (`ACTION_CREATE_DOCUMENT`). Экрана-просмотрщика
  у документа нет, сеть не участвует (НФТ-14/15). Состав и числа — из того же расчёта, что экран
  «История»: второй расчёт однажды разойдётся с первым и разойдётся незаметно.
- **Схема страницы** (A4 210×297 мм; боковые поля 18 мм, верхнее 18 мм, нижнее 16 мм; фон белый):

  ```
  Отчёт о приёме лекарств
  Склянка · профиль «Мама»
  Период: 1 — 30 сентября 2026
  Сформирован: 30 сентября 2026, 12:34
  ─────────────────────────────────────────────────
  СВОДКА
  Принято: 86 из 100 приёмов (86 %)
  Принято вовремя: 74 %
  Дней без пропусков: 9
  Пропусков за период: 12
  ─────────────────────────────────────────────────
  ПО ЛЕКАРСТВАМ
  Эутирокс · 1 таблетка · 50 мкг · 08:00       18 из 20 (90 %)
  с 1 марта, бессрочно · Пропусков нет
  Витамин D3 · 1 капсула · 2000 МЕ · 08:00     20 из 21 (95 %)
  с 6 марта, бессрочно · Пропуски: 3, 17 сентября
  Магний B6 · 2 таблетки · 48 мг · 08:00, 20:00   14 из 20 (70 %)
  12 сентября — 12 октября · Пропуски: 6, 9, 14, 21 сентября;
  из них 1 отмечен человеком, 3 — без отметки
  ─────────────────────────────────────────────────
  Не является медицинским документом      Склянка · стр. 1
  ```

- **Состав.** Шапка: название, «Склянка · профиль „Мама“» (имя активного профиля — решение
  ОВ-57), период (выбранный месяц), дата и время формирования. Сводка: доля принятого
  («Принято: 86 из 100 приёмов (86 %)» — сумма по строкам), «Принято вовремя: N %» по порогу
  ±15 мин (ОВ-80; пока порог не посчитан — прочерк, как на экране: выдуманное число в отчёте
  недопустимо), «Дней без пропусков», «Пропусков за период». По лекарствам — блок на каждое,
  включая архивные с пометкой «Курс в архиве» (ПР-11): строка с названием и справа «принято
  N из M (P %)», строка с дозой, расписанием и курсом («по потребности» — словами), строка
  пропусков с датами и разделением по природе («отмечен человеком» / «без отметки») — для врача
  это разные вещи (ОВ-12); «Пропусков нет», если их нет. Если за период нет ни одной записи —
  строка «За период нет ни одной записи о приёме», блок «По лекарствам» не печатается.
  Оговорка «Не является медицинским документом» — в колонтитуле каждой страницы; выводов,
  оценок и советов документ не содержит (приложение не медицинское изделие; проверяется тестом).
- **Вёрстка.** Блок одного лекарства не разрывается между страницами; шапка — только на первой
  странице, колонтитул — на каждой. Цвета — токены системы: текст `Text #241F1B`, вторичный
  `TextMuted #5F564D`, линии `Line #E6DED2`, акцентная линия под шапкой `Accent #B4512F`;
  профиль документ не перекрашивает — профиль назван словами, а печать не должна зависеть
  от цвета. Шрифты — те же два файла, что в приложении (§2), встраиваются в PDF: Literata 600 —
  название и числа сводки; Golos Text 400/600 — весь остальной текст. Кегли: название 20 pt,
  заголовки блоков 11 pt прописными, текст 10 pt, колонтитул 8–9 pt; межстрочный 1,35.
- **Имя файла:** существующий шаблон `report_file_name` с расширением `.pdf` —
  `sklyanka-report-ГГГГ-ММ.pdf` (месяц — начало периода); кириллица в имя не добавляется:
  файл уходит в чужие приложения и почту.
- **Путь передачи.** «Отчёт врачу» открывает существующую шторку: предупреждение «Отчёт содержит
  медицинские данные в открытом виде» и два действия — «Передать» и «Сохранить файлом»; оба
  отдают собранный PDF, отмена системного диалога даёт сообщение «Передача отчёта отменена»,
  повтор возможен. Текстовой сводки в шторке больше нет — документ один (PDF), и двух версий
  одного содержания не остаётся; вместо неё короткая строка состава (профиль, период, числа),
  чтобы человек видел, что отправляет.
- **Кто:** Дизайн; ОВ-15 решён ведущей сессией 29.09.2026 («PDF»).
- **Затрагивает:** `03-screens.md` («История»), `DoctorReportRenderer` (текстовая отрисовка
  заменяется PDF), ресурсы `report_file_name` / `report_media_type`; SKL-33.
- **Новые сущности:** нет; PDF — документ, а не экран приложения.

### ОВ-7 · Удаление профиля — уточнение по SKL-36
- **Где живёт действие.** «Настройки» → раздел «Профили» → последней строкой группы,
  за разделителем, — **«Удалить профиль „Мама“»**. Строка появляется только тогда, когда активен
  чужой профиль, и называет его по имени: удалить можно ровно тот профиль, в контексте которого
  человек находится, — а контекст виден по индикации чужого профиля (полоса, подкрашенная шапка,
  надпись «Профиль · Имя», баннер, акцент; ПРФ-11). Для своего профиля строки нет никогда
  (ПРФ-28). Карточка профиля для этого не заводится: управление профилями живёт в настройках,
  а действие — одно и необратимое.
- **Экран подтверждения** — отдельный, по образцу «Заменить всё» (ОВ-67; диалогов дизайн-система
  не содержит):
  - шапка с возвратом (отмена), заголовок «Удалить профиль?»;
  - «Профиль „Мама“ будет удалён вместе с данными:»;
  - числа потерь — теми же запросами, что строят список лекарств и историю профиля, без
    отдельного подсчёта: «Лекарства: 4 (в архиве 2)» — все лекарства профиля, активные
    и архивные; «Записи истории: 318» — все записи приёмов профиля. Нулевые числа показываются
    как есть;
  - «Напоминания о приёмах этого профиля будут сняты» (ПРФ-30);
  - предупреждение баннером (§4.6, вид «Предупреждение»): «Удаление необратимо: профиль и все
    его данные будут стёрты с этого устройства. Вернуть их будет нельзя»;
  - предложение выгрузки: второстепенная кнопка «Сохранить файл переноса» — та же выгрузка, что
    на экране «Перенос данных» (тот же файл и формат; второго механизма не заводится); пояснение
    «Файл содержит все профили. Вернуть „Мама“ можно будет только загрузкой всего файла». После
    успешного сохранения на экране появляется факт «Файл сохранён — 30 сентября 2026, 12:34»,
    кнопка остаётся доступной; отменённый системный диалог ничего не меняет. Выгрузка не удаляет
    данные и не заменяет подтверждение;
  - подтверждение словом (образец ОВ-67): подпись «Введите слово «Удалить», чтобы подтвердить»,
    поле и основная кнопка «Удалить профиль» цветом `--danger`; пока слово не введено, кнопка
    недоступна (§4.3, «недоступная»). Слово фиксированное, а не имя профиля: имя бывает длинным,
    а действие не должно становиться набором текста. Сравнение — без учёта регистра и краевых
    пробелов; неверный ввод — это недоступная кнопка, а не ошибка данных (ОВ-38 не применяется).
- **Финальное состояние.** Экран переходит в состояние результата: «Профиль „Мама“ удалён»,
  «Активным стал ваш профиль», кнопка «Готово» — возврат в «Настройки». Профиль и его данные
  удалены, из списка он исчез, будильники сняты (ПРФ-30), активным стал свой профиль и приложение
  показывает это явно (ПРФ-31). Точка невозврата — подтверждение словом; после неё отмены нет.
- **Кто:** Дизайн; ОВ-7 решён ведущей сессией 29.09.2026 (удаление с предупреждением
  и предложением выгрузить файл). Промежуточное «скрытие» профиля (ПРФ-29, SKL-15) этим
  решением снимается.
- **Затрагивает:** `03-screens.md` («Настройки» — строка и экран удаления), `06-profiles.md` §6
  (ПРФ-28, ПРФ-30, ПРФ-31; ПРФ-29 закрывается ответом ОВ-7), `08-design-system.md` (основная
  кнопка в `--danger`); SKL-36.
- **Новые сущности:** экран «Удаление профиля»; новых токенов нет (`--danger` заявлен
  ОВ-38/ОВ-67).
