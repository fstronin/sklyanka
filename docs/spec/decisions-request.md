# Запрос решений заказчику — остаток приёмки SKL-26

По итогам SKL-26 («Исполнимые экранные сценарии приёмки») 333 автоматизируемых исполнения
из 360 зелёные. Остальные 27 — не пропущенные шаги, а решения и этапы, которых не хватает,
чтобы закрыть сценарии. Этот документ собирает их в один список для заказчика.

Три пункта — **решения заказчика** (нужен ответ, после которого сценарий станет исполнимым).
Три пункта — **ожидание этапа или версии** (решение уже принято, работа вернётся вместе
с соответствующим этапом). Пункт 1 из исходного списка семи — предупреждение на «Сегодня» —
вынесен отдельной задачей [SKL-29](../tasks/SKL-29/), а не в этот запрос.

## Решения заказчика

### 1. Порог «принято вовремя» — `ОВ-80`

- **Сценарии:** SKL-18, два: «Сводка показывает три числа с подписями из макета» и «Доля
  принятого вовремя считается по согласованному порогу» (`@blocked`).
- **Что не хватает:** порога, по которому приём считается принятым «вовремя». Сейчас плитка
  сознательно показывает прочерк (`OnTimeRule.NotAgreed`).
- **Кто решает:** заказчик.
- **Варианты:** фиксированный интервал от назначенного времени (±15/±30 минут);
  подпись «принято» без слова «вовремя»; оставить прочерк.
- **Где зафиксировано:** `docs/spec/12-open-questions.md`, `ОВ-80` (расширенный раздел там же).

### 2. Размер упаковки — `ОВ-45`

- **Сценарии:** SKL-10, два: «9 таблеток из 60» и полоса остатка.
- **Что не хватает:** в модели данных нет размера упаковки, только `stock_left`; знаменатель
  «из 60» и полосу заполнения выводить не из чего.
- **Кто решает:** заказчик + разработка.
- **Варианты:** завести поле размера упаковки (схема SKL-04, форма SKL-09, перенос SKL-19);
  считать знаменателем максимальный остаток; убрать знаменатель и полосу.
- **Смежно:** `ОВ-13` (что делает «Пополнить») и `ОВ-46` (арифметическое расхождение в макете).
- **Где зафиксировано:** `docs/spec/12-open-questions.md`, `ОВ-45`, `ОВ-13`, `ОВ-46`.

### 3. Строка «Разрешения и автозапуск» — `ОВ-48`

- **Сценарий:** SKL-14, один: «Повторный вход из настроек открывает тот же экран без
  индикатора шагов».
- **Что не хватает:** строка настроек ведёт в диагностику, а не в онбординг; два источника
  спеки называют разные цели одной строки (НАП-21 против НАП-37).
- **Кто решает:** заказчик + дизайн.
- **Варианты:** один экран с двумя частями; два экрана (строка в онбординг, диагностика
  отдельной строкой); строка в состояние разрешений, онбординг кнопкой оттуда.
- **Смежно:** `ОВ-49` (где живёт экран диагностики) и `ОВ-50` (кнопка пробного напоминания).
- **Где зафиксировано:** `docs/spec/12-open-questions.md`, `ОВ-48`, `ОВ-49`, `ОВ-50`.

## Ожидание этапа или версии

Решение уже принято, сценарий ждёт не ответа, а наступления события. Эти пункты сюда — чтобы
полный список остатка был в одном месте, а не потому, что по ним нужен ответ.

### 4. Часы отложены — `ADR-0009`

- **Сценарии:** 12 — строки и рубрики часов (SKL-10 — переключатель и `@a11y`-структура;
  SKL-20 — рубрика «Часы и система», пример «Часы Huawei», строка состояния связи).
- **Что происходит:** Wear Engine отложен до пост-MVP решением
  `docs/spec/adr/ADR-0009-wear-engine-post-mvp.md`. Строки часов в первой версии нет
  по решению, сценарии ждут возвращения этапа.
- **Возвращение:** начинается с заявки SKL-01 (самая длинная по сроку), затем SKL-16, SKL-17.

### 5. Экран подключения часов — SKL-17

- **Сценарий:** SKL-14, один: «Пройденная цепочка ведёт дальше» (ведёт на экран часов).
- **Что происходит:** задача SKL-17 отложена (пост-MVP, `ADR-0009`). Продукт намеренно ведёт
  на «Сегодня», исход `WATCH_SETUP` вычисляется и попадает в журнал. Закроется вместе с SKL-17.

### 6. Файл более старой версии формата — SKL-19

- **Сценарий:** SKL-19, один: «Файл от более старой версии формата читается с предупреждением».
- **Что происходит:** сейчас `TransferFormat.CURRENT_VERSION = 1`, список миграций пуст —
  файла старше первой версии не существует. Сценарий появится со второй версией формата,
  тогда же появится первый настоящий шаг миграции.

## Как ведётся

Решения заказчика (пункты 1–3) закрываются в `docs/spec/12-open-questions.md` и сразу
делают исполнимыми соответствующие сценарии в `acceptance.feature` их задач. Ожидания
этапа (пункты 4–6) закрываются самим наступлением этапа; их сценарии остаются помечены
`UNDEFINED` до тех пор, и это честно видно в `acceptanceRun`.
