# ADR-0001. Стек: Kotlin, Jetpack Compose, Room, Hilt, minSdk 26

## Статус

Принято. 26 сентября 2026. Зафиксировано в `CLAUDE.md` и `PLAN.md`.

## Контекст

Приложение работает на Android 8.0 и выше, основная цель — EMUI, эталонное устройство —
Huawei с EMUI 15 (`design/SPEC-original.md §2`). Google Play Services не предполагаются.
Магазины — AppGallery и RuStore.

Продукт держится на трёх вещах, и все три упираются в платформу:

1. **Точные будильники.** `AlarmManager.setExactAndAllowWhileIdle`, перепланирование по
   `BOOT_COMPLETED` и смене часового пояса, разрешение `SCHEDULE_EXACT_ALARM`, обход
   агрессивного энергосбережения EMUI (`§5`). Это прямая работа с платформенными API
   и системными приёмниками.
2. **Каналы уведомлений.** Два статичных канала, полноэкранное напоминание, поведение
   каналов, которое нельзя изменить после создания (`§5`, `ADR-0004`).
3. **Wear Engine SDK.** Нативная библиотека Huawei: `HiWear.getNotifyClient()`,
   `NotificationTemplate`, колбэк `Action.onResult` (`§6`). Официальной поддержки
   не-нативных платформ нет.

Четвёртое обстоятельство — дизайн-система. `§9` задаёт визуальный язык в виде набора
токенов, а `docs/spec/08-design-system.md` разворачивает его в токены цвета, типографики,
геометрии и каталог компонентов с перечислимыми состояниями.

Минимальная версия API диктуется двумя вещами сразу: каналы уведомлений появились в API 26,
и с API 26 же начинается поведение Doze, ради которого существует
`setExactAndAllowWhileIdle`. Ниже 26 продукт просто не имеет смысла.

## Решение

Kotlin, Jetpack Compose, Room, Hilt, AlarmManager, Wear Engine SDK. `minSdk 26`.

- **Kotlin** — язык платформы; корутины дают внятную модель для работы приёмников и базы.
- **Jetpack Compose** — интерфейс. Токены дизайн-системы становятся объектами
  (`SklyankaColors`, `SklyankaType`, `SklyankaShapes`, `SklyankaSpacing`), компоненты —
  функциями с перечислимым состоянием, подмена акцента на цвет профиля — темой.
- **Room** — хранение. Типизированные миграции с тестами (`НФТ-9`), доступ из корутин,
  генерация запросов на этапе компиляции.
- **Hilt** — связывание. Приёмники будильников и уведомлений получают зависимости
  штатным способом (`@AndroidEntryPoint`), а источник времени подменяется в тестах
  (`НФТ-48`).

## Последствия

- Приложение остаётся нативным Android-приложением без промежуточного слоя: любое
  платформенное API доступно напрямую и немедленно, что для точных будильников и Wear
  Engine решающе.
- Дизайн-система выражается кодом, а не соглашением: правило «токены не хардкодятся по
  месту» проверяется правилом lint (`НФТ-47`), а не обзором.
- Доменный слой остаётся свободным от Android и тестируется на JVM (`НФТ-46`).
- Плата — привязка к одной платформе. Версии для iOS не будет без переписывания
  интерфейса; учитывая, что продукт завязан на часы Huawei и EMUI, это не потеря.
- Плата — Compose на Android 8.0 не самый быстрый: холодный старт нужно измерять
  (`НФТ-21`) и при необходимости оптимизировать базовыми профилями.
- `minSdk 26` отсекает Android 7 и ниже. Для продукта, чьё требование — надёжное
  напоминание, эти версии всё равно непригодны.

## Альтернативы

**Kotlin с XML-разметкой.** Проверенный подход, меньше риска с производительностью на
старых устройствах. Отвергнут: дизайн-система из токенов ложится на XML через темы и
атрибуты, но состояния компонентов (карточка приёма имеет шесть состояний) приходится
собирать селекторами и кодом, а смена акцента на цвет профиля — перекрашиванием темы на
лету, что в XML делается неудобно и неполно. Объём экранов (пятнадцать по `§4`, у каждого
несколько состояний) делает разницу заметной.

**Flutter.** Один код на две платформы, быстрая разработка интерфейса. Отвергнут по трём
причинам. Wear Engine SDK нативный — потребовалась бы платформенная обвязка ровно для той
части, от которой зависит продукт. Точные будильники, приёмник `BOOT_COMPLETED`, каналы
уведомлений и полноэкранное уведомление всё равно пишутся на платформе, и вся хрупкая
часть оказывается в самодельном мосту. Вторая платформа при этом не нужна: продукт завязан
на EMUI и часы Huawei.

**React Native, KMP с общим UI и прочие кроссплатформенные варианты** отвергнуты по той же
причине, что Flutter: выигрыш там, где выигрыш не нужен, и потери там, где продукт живёт.
